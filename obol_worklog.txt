Original Obol Pivot Migration Plan
----------------------------------

Purpose
-------

BRL-CAD should use Obol as the canonical scene, view, interaction, and
rendering API for interactive 3D applications.

The migration is parallel-first: build the Obol path beside the current
BSG/DM path until it reaches production parity, then remove public libbsg,
libdm, dm_plugins, and BSG/DM-shaped application APIs.  Temporary internal
bridges are allowed while a phase is incomplete.  No long-lived public BSG
or DM compatibility layer is part of the target design.

libbrlobol is the BRL-CAD-specific Obol extension library.  It should define
BRL-CAD Obol nodes, actions, details, and narrow application services.  It
must not become a generic replacement for BSG's render-item/backend-scene
model.

The first production target is qged/qtcad.  After qged is usable on Obol,
migrate GED/TclCAD/mged, then remove lower-level BSG/DM utility
dependencies.


Guiding Decisions
-----------------

* Obol cameras, transforms, SoViewport, SoRenderManager, actions, nodes,
  fields, and details are authoritative for scene, view, render, and
  interaction state.
* New drawing code should use Obol directly or use BRL-CAD Obol extensions.
  It should not add new BSG/DM dependencies outside explicit legacy
  allowlists.
* BRL-CAD-specific policy belongs in libbrlobol.  Generic scene graph,
  traversal, rendering, text, picking, and backend features should be exposed
  through Obol rather than rewrapped as parallel BSG concepts.
* C++ is acceptable for code that directly interacts with the drawing API.
  C and Tcl callers may use opaque bridges backed by Obol.
* bg_vlist and bg_line_layer are low-level geometry/debug containers, not
  scene APIs.  Application-visible drawing state should be Obol nodes.
* UNIX plot3 and TIG-style helpers are legacy plot/export/diagnostic support.
  They should not become Obol scene concepts.
* bg_line_layer should stay independent from plot3.  It is an in-memory
  diagnostic/overlay container; plot3 is a legacy file-stream format and
  helper API.  Conversion helpers between bg_line_layer, plot3 output, and
  Obol overlay nodes are appropriate, but moving line_layer into plot3.h
  would couple normal diagnostic geometry to a legacy export format.
* Scene text, labels, HUD text, and annotations should use Obol 2D/3D text.
  If flattened text geometry is needed, use an Obol-backed text-to-geometry
  conversion/export path rather than preserving vectfont as a scene API.
* Obol's pluggable backend model is the intended replacement for libdm's
  rendering/display role.
* libimgstream is the target home for live mutable image streams, async image
  producers, dirty-update notification, transport, and framebuffer protocol
  compatibility.  It is not a display backend system.
* libicv remains the target home for static image containers, codecs, image
  file I/O, image transforms, and neutral lookup-table/colormap operations.
* Obol owns image display, placement, layering, texture upload, readback, and
  rendering backend selection.  Framebuffer pan/zoom/cursor/overlay behavior
  is display compatibility state realized through Obol/application display
  hosts, not core image-stream storage.
* fb compatibility belongs inside libimgstream as a clearly scoped
  compatibility layer while callers migrate.  It should preserve useful
  host:port, ipc:<addr>, PKG_ADDR, FBSERV_TOKEN, FBSERV_TLS, and MSG_FB*
  workflows without preserving libdm's framebuffer backend abstraction.


Current State
-------------

libbrlobol and qtcad:

* brlobol_init registers BRL-CAD Obol classes and supports replacing the
  active Obol context manager after initial setup.
* BRLObolViewController owns the application scene root, active camera,
  SoViewport, SoRenderManager, viewport region, and render-request lifecycle.
* qtcad canvases expose the Obol controller and an Obol viewport image
  readback path.
* qtcad installs an application-owned Obol context manager backed by Qt
  offscreen GL, with OSMesa fallback when Qt offscreen creation is not
  available.
* qtcad GL/SW viewport capture uses Obol readback directly when migrated Obol
  scene content exists, consumes the Obol render request, and does not
  initialize the legacy display manager for that content.  SW visible paint
  follows the same direct Obol readback path.  GL migrated-content paint now
  renders through BRLObolViewController::renderPending with the Qt GL context
  current before legacy DM initialization, and falls back to legacy DM drawing
  only when Obol rendering is not available.
* qtcad default keyboard/mouse/wheel navigation no longer requires a legacy
  display manager before it can update the transitional view and synchronize
  Obol camera/render state.
* qtcad point, rectangle, and ray selection filters prefer Obol pick identity
  for migrated content and do not initialize the legacy display manager when
  Obol supplies the selection paths.  The public qtcad selection filter API
  now exposes normalized paths instead of BSG pick/interaction result
  accessors, and the qged selector plugin consumes those paths directly.
  The qtcad point-pick helper also has the first nonblocking source-backed
  exact mesh pick integration: it keeps ordinary display picks as the first
  pass, then uses SoBRLSourceMeshPickAction, request-filtered LoD result
  draining, and source-backed request submission for LoD meshes explicitly set
  to full-detail picking.  Rectangle picks inherit this through their point
  samples.  qtcad point and rectangle picks also use the libbrlobol direct
  librt exact ray helper as a database-source fallback for implicit solids and
  implicit-backed combs when no ordinary display/source-backed mesh hit is
  available.  Legacy BSG pick paths remain internal fallback.
* qtcad Obol measurement and snap workflows operate on migrated content
  without initializing the legacy display manager.  Measurement overlays are
  now published exclusively through Obol; the qtcad measurement filter no
  longer creates BSG measurement features or caches BSG measure-result
  records, and 3D measurement no longer falls back through BSG pick
  candidates or direct raytrace prep.  qtcad now exposes a full-detail snap
  helper that consumes matching ready source-backed LoD results or submits
  missing source-backed requests through SoBRLSnapAction, while the ordinary
  interactive snap helper remains display-level.  qtcad also exposes an exact
  full-detail geometry measure helper that consumes matching source-backed
  LoD results through SoBRLMeasureAction and reports source-backed counts,
  bounds, area/length, and nearest-primitive identity.  qtcad exact
  pick/snap/measure submissions now pass BRLObolViewController's exact
  full-detail face/point budget to source-backed provider tasks so
  over-budget whole-object reloads can fall back before mesh allocation.  Snap
  retains
  transitional legacy refinement fallback for non-migrated or view-scoped
  cases.
* qtcad Obol workflow tests cover pinewood.g, havoc.g, and the larger
  mixed-primitive m35.g sample, including real-model readback, pick, snap,
  and measurement overlay helpers.  doc/notes/obol_realization_coverage.txt
  now records share/db/faa/Generic_Twin.g as the larger FAA maturity candidate
  once the large-model staged-LoD path is ready for routine gating, and
  test_qtcad_obol_real_models exposes it as an opt-in
  BRLOBOL_QTCAD_GENERIC_TWIN=1 draw/readback check.
* libbrlobol mesh face picks now preserve the picked triangle's source
  coordinate indices in SoBRLPickDetail, and SoBRLExportAction triangle
  records carry the same vertex-index identity.  Face pick details also record
  the nearest source edge endpoints, nearest source vertex, and object-space
  hit point for deterministic mesh sub-entity inspection.  Full standalone
  edge and vertex picking remain queued.
* libbrlobol BoT mesh realization now copies existing RT-owned mesh LoD
  metadata onto SoBRLMeshShape fields when a neutral rt_mesh_lod cache result
  is already available.  It records active level, counts, snapped-point/normal
  flags, and bounds without exposing BSG LoD containers or forcing synchronous
  cache generation during normal Obol realization.  The bridge now expresses
  that copied metadata as a provider-neutral BRLObolLodRequest/Result and
  geometry-handle record before publishing the existing Obol fields.
  SoBRLExportAction triangle records now carry that same copied LoD summary
  for diagnostic export and staged-realization verification.
* libbrlobol now has the first provider-neutral BRLObolLodService skeleton
  for staged realization work.  It owns explicit start/stop, joinable worker
  threads, generation cancellation, dependency-aware task scheduling, UI-thread
  result draining, in-flight diagnostics, cancellable task-level debug delay
  controls, stale result rejection, owned realization-task data cleanup, and
  one serialized cache-write lane without exposing BSG LoD APIs.  It also has
  the coalesced result-ready wakeup described in the consolidated LoD notes:
  workers only signal that queued results should be drained, and the owning
  view/controller performs the main-thread drain/apply pass.  The LoD result
  contract now carries typed Stage 0/1/2 directory/dependency records, display
  attributes, AABB results, and proxy/OBB payloads so early placeholder states
  can be generated and inspected before final mesh payloads arrive.
  SoBRLMeshShape can now consume staged LoD results into Obol fields, reject
  stale result keys, and publish cached RT mesh results through the same
  staged-result path.  Staged mesh results can now carry an owned Obol-side
  triangle payload copied from an active RT mesh-LoD data view, and
  SoBRLMeshShape can apply that payload through its existing indexed-triangle
  fields without borrowing RT or BSG arrays.  SoBRLMeshShape can also build a
  provider-neutral BRLObolLodRequest from its Obol identity, policy, counts,
  and bounds fields, and BRLObolViewController can derive a sanitized
  rt_view_info snapshot from its Obol camera and viewport state.  The first
  SoBRLMeshLodSubmitAction can walk Obol mesh nodes, build deterministic
  requests from those fields, own RT mesh-cache provider state through the
  service task lifetime, and submit view-driven cached mesh refresh/load work
  explicitly.  BRLObolViewController now exposes a narrow controller hook that
  derives the active rt_view_info snapshot, submits per-database-source mesh
  LoD requests through that action, drains completed service results, and
  applies them back through the update action while recording counts and
  diagnostics; it can retain an active LoD service subscription, mark pending
  results from the wakeup callback without touching scene nodes, and process
  those results before rendering.  It also has the first coalesced auto-submit
  gate for changed view/policy/source signatures, so render-time preparation
  can enqueue fresh RT mesh-cache provider work without duplicate submissions
  for the same stable scene.  The first SoBRLLodUpdateAction drains LoD service
  results on the UI/main thread, matches them to SoBRLMeshShape nodes by
  source path/name, applies accepted staged fields and owned mesh payloads,
  and records rejected or unmatched result diagnostics.  The first RT
  mesh-cache provider task can refresh/load cached RT mesh LoD through the
  service, optionally force a requested RT LoD level, shrink active RT arrays
  after copying, and return the neutral staged mesh result with an owned mesh
  copy.  SoBRLLodMeshShape now provides
  the first dedicated LoD-backed BoT mesh representation while preserving the
  existing SoBRLMeshShape full-field path for small or synchronous meshes, and
  LoD submission filters ordinary meshes unless explicitly configured
  otherwise.  BoT database realization now uses lodBotThreshold so the
  full-mesh path remains default and only threshold-matching BoTs become
  LoD-backed.  SoBRLMeshShape now has an explicit full-detail preservation
  policy: ordinary meshes preserve their pre-LoD indexed triangles when
  applying an active display-LoD payload, while SoBRLLodMeshShape opts out of
  that backup and keeps lightweight source counts/bounds for stable request
  identity after the full-detail fields are replaced.  For preserving meshes,
  SoBRLExportAction/SoBRLMeasureAction/SoBRLSnapAction can use that preserved
  source geometry for full-detail/detail-preserving policy requests while
  DISPLAY_LEVEL continues to use the displayed LoD mesh.  When no preserved
  full-detail payload is resident, exact export/measure/snap now record
  BRLObolSourceMeshRequest records carrying source identity, counts, and
  bounds instead of treating display LoD as exact geometry.  The first RT
  source full-detail provider can reload direct BoT source objects into owned
  Obol mesh payloads through BRLObolLodService, validates source-count
  mismatches as stale results, and exposes whole-object face/point limits so
  callers can refuse over-budget full-detail reloads before falling through to
  chunked detail reads.  BRLObolViewController now owns a per-view exact
  full-detail budget, and qtcad exact pick/snap/measure submit paths pass
  those limits to source-backed provider tasks.  Export, measure, and snap
  actions can now convert their recorded source requests into submit-ready RT
  full-detail LoD requests, and BRLObolLodService can submit those source
  requests with provider-owned cleanup.  Those actions can also consume
  returned full-detail mesh payloads using the recorded transform and
  shape-level metadata, and now expose action-level submit and drained-result
  consume helpers for recorded source-backed requests.  Higher-level
  exact-operation callers no longer need a separate triangle ingestion path
  for export, measure, or snap, but still need to call the helpers around
  their UI/tool workflows.  Exact mesh picking now has a matching
  source-backed traversal action that records full-detail source requests for
  LoD-backed meshes in exact-pick mode, can submit them through the LoD
  service, and can consume drained full-detail results via the shared
  pick-result ray tester.  qtcad point and rectangle picking now route exact
  mesh picks through that action around provider drain points without blocking
  the UI, and qtcad's explicit full-detail snap helper routes exact snap
  queries through the snap action source-backed drain/submit path.  qtcad's
  full-detail geometry measure helper now routes exact measurement queries
  through the measure action source-backed drain/submit path.  Other
  exact-operation tools still need matching caller-side drain/submit
  integration.  The LoD service now supports request-filtered
  result draining, which lets
  source-backed exact-operation callers consume matching full-detail results
  without stealing unrelated display-LoD results from the shared queue.  Snap
  and pick source-backed exact requests now carry source-local query metadata
  into LoD provider params: snap records bounded query boxes and tolerance,
  while pick records source-local rays.  This gives the future chunked BoT
  reader the object identity and query scope needed to avoid whole-object
  reloads, while leaving the current whole-direct-BoT provider behavior
  unchanged.
  Mesh ray
  picking now has the same initial policy split: display-level is the viewport
  default, while explicit full-detail picks use resident preserved source
  triangles when available and otherwise refuse to treat an active display-LoD
  payload as exact geometry.  That preservation is an interim correctness
  bridge for meshes that are already resident, not the target policy for large
  geometry.
  Production LoD-backed BoTs must be
  source-backed and memory-budgeted, keeping identity/bounds/active display
  payloads resident while exact operations fetch full-detail or bounded chunks
  from the .g/RT provider path on demand.  Exact picks for CSG implicit solids
  and implicit-solid-backed comb instances should use a librt ray query rather
  than tessellated display geometry.  libbrlobol now has the first direct
  librt ray helper for explicit database object paths; it returns the nearest
  implicit/comb hit with point, normal, distance, region/material data, source
  primitive name/type, and BRL-CAD pick-detail identity.  qtcad point and
  rectangle picks now call that helper for database-source implicit/comb
  fallback hits, including camera-derived rays for scenes that have database
  sources but no display-pickable Obol geometry.
  POP payload ownership, active-level selection, action/pick consumption of
  source-backed full-detail reloads, chunked detail reads from the recorded
  source requests when no preserved payload is resident,
  optional coarse POP-build spatial/index sidecar metadata for targeted exact
  picks/snaps, remaining tool integration of the librt exact-pick helper,
  prep cache ownership for repeated exact rays, result-order refinement across
  display/source-backed/librt hits, and richer policy-aware provider
  scheduling are still queued.
* libbrlobol shaded PNTS realization now preserves basic RT_PNT_TYPE_PNT
  point clouds as Obol vlist point primitives rather than failing the shaded
  path or forcing a mesh.  SoBRLVListShape exposes point primitive inspection,
  SoBRLExportAction exports point records with source identity, snap treats
  point primitives as endpoint candidates, and prototype tests cover shaded
  PNTS realization, bbox, pick detail, export, and snap behavior.  Richer PNTS
  point attributes such as per-point color, scale, and normal remain queued.
* qtcad still has a transitional BSG-to-Obol camera bridge.  The bridge is
  correctly kept in libqtcad, not libbrlobol.
* qtcad's visible rendering path is still transitional.  Obol render/readback
  works and GL/SW migrated-content paints bypass libdm, but libdm/BSG are
  still part of current application rendering for non-migrated content and
  legacy fallback paths.

Dependency guardrails:

* brlobol_pivot_guard is active as a transitional CTest guard.
* The guard blocks new BSG/DM leakage in Obol-canonical code and rejects
  direct BSG vlist/vlblock symbols in libbrlobol.
* doc/notes/obol_legacy_dependency_inventory.txt records the phase-owned
  direct BSG/DM dependency rows for the Obol pivot, and the guard checks the
  exact rows against src/source_dirs.cmake.
* The guard checks that qtcad Obol workflow tests do not directly link libdm,
  libbsg, or dm_plugins while they exercise the transitional application path.
* The guard rejects reintroducing BSG measurement feature/result fallback
  symbols or the old BSG-pick/raytrace 3D measurement fallback in
  QgMeasureFilter while the rest of qtcad continues its staged migration.
* The guard rejects reintroducing public BSG/raytrace selection accessors in
  QgSelectFilter and direct BSG interaction consumption in the qged selector
  plugin.
* The guard checks that the default plot3 implementation is owned by the
  normal libbg implementation unit and is not reintroduced through libbsg or
  standalone bg test executables.  It also checks that bg_line_layer keeps
  its explicit plot3 diagnostic export helpers and that standalone plot3
  utilities do not relink libbsg.
* The framebuffer/image-stream plan records the split: libimgstream owns
  non-display stream storage, transport, producer/subscriber lifecycle, and
  fb compatibility; libicv owns static images/codecs/lookup tables; Obol and
  libbrlobol own image display and window-host behavior.
* The initial libimgstream target now provides an opaque imgstream_* C API for
  RGB/RGBA memory streams, resize, clear, full-frame and rectangle
  read/write, stream info/metadata snapshots, dirty-region generation,
  subscriber notification, producer begin/end state, and icv_image_t snapshot
  conversion without linking libdm, libbsg, or libbrlobol.
* libbrlobol now provides SoBRLImageSource as the first Obol image-stream
  source ownership node.  It can wrap static icv_image_t data or borrowed
  libimgstream streams, tracks stream metadata/revisions in Obol fields, and
  subscribes to dirty-region notifications.  SoBRLViewportImage and
  SoBRLImagePlane are the first display consumers: they read source streams,
  rebuild standard Obol texture quads when source data/dirty revisions change,
  and expose the viewport/image-plane policy fields needed by framebuffer
  display migration.  Incremental backend dirty-region texture uploads and
  real window-host integration remain queued.
* The first libimgstream framebuffer compatibility unit is in place as
  imgstream/fb_compat.h and src/libimgstream/fb_compat.c.  It maps memory
  framebuffer requests to RGB imgstream buffers, preserves legacy view,
  window, zoom, cursor, screen-cursor, and cursor-shape compatibility
  spellings plus reset, viewport, poll, and poll-rate compatibility as
  non-display state/operations, supports RGB and BW rectangle compatibility,
  and supports raw RGB file sink/source compatibility for
  ordinary file paths plus explicit /dev/disk:<path> or /dev/disk=<path>
  spelling.  It also supports /dev/stack fan-out to memory/file child sinks
  and /dev/null, /dev/debug, and /dev/txt diagnostic sinks without a display
  backend.  It preserves legacy 256-entry RGB colormap state through a neutral
  imgstream_fb_colormap type and rmap/wmap compatibility calls.  It classifies
  and normalizes remote/display specifiers through imgstream_fb_spec_info,
  including numeric port specs, host:port, host:port:device, tcp:, ipc:, and
  display framebuffer names.  Display-capable framebuffer opens now create an
  RGB stream and delegate open/close, view, cursor, viewport, flush, reset,
  and poll behavior to a registered toolkit-neutral display host callback;
  without that callback they still fail explicitly until the Obol/libbrlobol
  display-host migration connects real windows.
* The guard still needs to grow as more directories become Obol-canonical.

What We Should Not Rebuild
--------------------------

Do not recreate BSG inside libbrlobol.

The earlier BSG direction was useful because it separated application drawing
state from individual display backends.  Obol already provides the stronger
version of that model: a real scene graph, traversal/actions, details,
render managers, text, cameras, and pluggable backends.  The cleaner long
term design is to put BRL-CAD-specific behavior into Obol extensions and let
applications use Obol features directly.

libbrlobol may provide narrow controllers and services where BRL-CAD needs
coordination, such as database realization, diagnostics, edit preview, and
application render scheduling.  Those services should hold Obol objects and
BRL-CAD policy, not generic render lists, payload stores, or backend-neutral
scene abstractions parallel to Obol.


Target Public API Shape
-----------------------

libbrlobol:

* brlobol_init initializes Obol and BRL-CAD Obol classes.
* Database source nodes own BRL-CAD database/path realization state as
  normal Obol node fields.
* BRLObolViewController coordinates scene root, camera, SoViewport,
  SoRenderManager, render scheduling, readback, realization, and diagnostics.
* Realization, export, snap, measure, pick, diagnostics, edit preview, HUD,
  overlays, and text are expressed as Obol nodes/actions/details.
* SoBRLSceneController remains a narrow realization/diagnostic service.
* No public bsg_render_item, bsg_backend_scene, generic payload store, or
  BSG-like render list appears in libbrlobol.

qtcad/qged:

* Migrated code uses BRLObolViewController and Obol scene/camera objects.
* Existing bsg_view, dm, and fb accessors remain only during parallel
  migration.
* Final public drawing APIs do not expose bsg_view, dm, fb, or dm_plugins.
* vlist is not exposed as an application scene abstraction.  Wire output is
  converted to Obol line/shape nodes at the scene boundary.

GED/TclCAD/mged:

* GED drawing services update Obol database source nodes, Obol camera/view
  state, and Obol selection/pick details.
* C/Tcl callers use an opaque bridge backed by Obol where needed.
* No public BSG/DM compatibility shim survives final removal.

Image streams, framebuffer compatibility, and window hosting:

* libimgstream provides opaque imgstream_* stream lifecycle, metadata, pixel
  read/write, rect update, snapshot, subscriber, producer, and transport APIs.
* libimgstream/fb_compat preserves the current framebuffer API/protocol
  spellings needed by rt, remrt, fbserv, GED/TclCAD, and src/fb tools while
  translating them to image-stream storage, transport, or explicit
  unsupported diagnostics.
* SoBRLImageSource represents static icv_image_t data and live libimgstream
  streams as Obol data sources.
* SoBRLViewportImage displays an image source in viewport-aligned underlay,
  overlay, HUD, render-progress, and framebuffer-compatibility roles.
* SoBRLImagePlane displays an image source as a textured scene-space plane.
* libbrlobol owns the toolkit-neutral BRLObolWindowHost contract around
  BRLObolViewController, normalized input events, semantic input profiles,
  and display-host callbacks used by display-capable fb_open and dm_open
  compatibility.  The neutral contract and initial imgstream display-host
  bridge are in place; display-capable framebuffer streams can attach to
  SoBRLImageSource and SoBRLViewportImage nodes under the controller.
  BRLObolHeadlessWindowHost provides the first offscreen adapter and drains
  those streams through Obol readback; qtcad's QgObolWindowHost provides the
  first Qt canvas adapter for the same display-host contract and can create an
  owned visible Qt toplevel QgSW fallback when no qtcad canvas exists.  General
  dm_open routing, final Qt host selection, and Tk/MGED adapters remain.
* libimgstream must not depend on libbrlobol.  Display-capable framebuffer
  compatibility obtains or creates an image stream, then delegates window or
  viewport display through a registered libbrlobol/application display host.

Migration Phases
----------------

Phase 1: Architecture freeze and guardrails

* Document Obol as BRL-CAD's canonical drawing API.
* Keep brlobol_pivot_guard active in transitional mode.
* Inventory all current BSG/DM dependencies.
* Convert the guard to strict mode before hard removal.

Done when:

* The policy is documented.
* New Obol-canonical directories are clean of BSG/DM dependencies.
* Legacy violations are inventoried and assigned to later phases.

Phase 2: Productionize libbrlobol

* Complete primitive and hierarchy realization.
* Add staged provider-neutral LoD realization for large BoTs, starting with
  POP behind the RT mesh-LoD facade and preserving full-detail fallback for
  exact operations.
* Preserve identity, material, visibility, selection, draw intent, edit
  preview, and diagnostics on Obol nodes/fields/details.
* Implement snap, measure, pick, export, partial refresh, HUD, overlays,
  faceplate, grid, axes, ADC, and text behavior with Obol concepts.

Done when:

* libbrlobol can load, realize, inspect, select, pick, snap, measure, export,
  and render the agreed model set without libbsg/libdm.
* Large BoTs can render through LoD-backed Obol geometry, refine from view
  changes, and still support explicit full-detail pick/measure/snap/export
  policies.
* Controller rebuild from an existing Obol scene works without lost state.
* libbrlobol has no generic BSG replacement API.

Phase 3: Migrate qged/qtcad

* Replace visible qtcad rendering with Obol rendering.
* Move qged open/draw/erase/view/autoview/navigation/pick/select/snap/
  measure/edit-preview/HUD/screenshot workflows to Obol.
* Use Obol software/offscreen fallback paths instead of libdm swrast.

Done when:

* qged/qtcad render real models through Obol only.
* qged/qtcad support the expected interactive workflows through Obol.
* qged/qtcad no longer link libbsg/libdm or depend on dm_plugins.

Phase 4: Migrate libged, libtclcad, and mged

* Replace bsg_ged_draw* with an Obol-backed GED scene service.
* Port TclCAD view creation, input handling, refresh, faceplate, and readback
  to the Obol controller bridge.
* Keep mged supported with a proper Tcl/Tk Obol widget for performant native
  rendering when system graphics APIs are available.  Obol offscreen rendering
  plus Tk image presentation is a fallback path, not the target design.
* Route display-window creation through the libbrlobol window host contract
  rather than preserving dm_open as a public display-manager abstraction.

Done when:

* libged and libtclcad no longer link libbsg/libdm.
* mged core display workflows pass scripted regression tests using Obol.
* No GED/TclCAD command requires a public bsg_view or dm object.

Phase 5: Remove lower-level BSG/DM dependencies

* Finish moving neutral geometry/debug/export containers to libbg/librt names.
* Retire BSG vlist and line-layer wrappers.
* Replace scene text and labels with Obol text.
* Grow libimgstream from the initial memory-stream target into the owner of
  useful framebuffer storage, streaming, producer/subscriber, transport,
  fbserv, and fb compatibility behavior.
* Move static image/codecs/lookup-table behavior to libicv.
* Replace libdm framebuffer display behavior with Obol image nodes and
  libbrlobol display-host/window-host paths.

Done when:

* No non-legacy target in src/source_dirs.cmake depends on libbsg/libdm.
* Low-level libraries do not include BSG/DM headers for scene or display
  behavior.
* Framebuffer tools use libimgstream/fb_compat, libicv, or Obol readback and
  display paths rather than libdm framebuffer backends.

Phase 6: Hard removal

* Delete installed BSG and DM public headers.
* Delete libbsg, libdm, and dm_plugins from build and install.
* Remove temporary allowlists and transitional bridges.
* Remove obsolete fb_* compatibility wrappers only after rt, remrt, qged,
  TclCAD/mged, and required tools use libimgstream or Obol directly.  Keep
  transport and MSG_FB* compatibility where it remains useful independent of
  the old libdm framebuffer backend API.
* Update documentation, examples, man pages, package metadata, pkg-config
  files, and build files.
* Enable strict dependency checks.

Done when:

* Full build/install produces no libbsg, no libdm, no dm_plugins, and no
  public BSG/DM headers.
* No source target links libbsg/libdm.
* No source code includes BSG/DM headers outside intentionally archived
  historical documentation.
* Obol is documented as the canonical BRL-CAD scene API.


Consolidated Historical Notes
-----------------------------

This section preserves the useful context from the former root notes that were
not meant to stay as separate active handoffs.

newdraw branch review:

* The newdraw branch was a large architectural migration, not a cosmetic
  libbv rename.  The review snapshot measured roughly 1050 changed files,
  155298 insertions, and 42636 deletions.
* The strongest value in newdraw was centralized semantic drawing state:
  libged owned draw records, draw transactions, database indexes, selection
  state, stale tracking, and shared frontend semantics; libdm gained a backend
  render-item/resource-cache boundary; MGED, TclCAD, and qged moved toward one
  common draw-state model.
* The main risk was scope and public API stability.  libbsg was broader than
  libbv: scene graph, view state, render items, payloads, selection, snapping,
  overlays, HUD, LoD, and backend adapters.  The Obol migration keeps the
  useful semantic lessons but avoids preserving libbsg as the canonical public
  drawing API.
* The review's validation lesson still applies: make the risk bounded with
  main-compatible behavioral tests, unchanged tests on the migrated path,
  Obol/newdraw-only semantic tests, stress/scale/performance gates, and an
  explicit evidence package before broad legacy removal.

Modern drawing/model handoff:

* The database remains authoritative.  Draw records, selections, edit
  previews, Qt models, indexes, and application state are derived and
  rebuildable.
* Native GED services are the desired ownership model:
  GedDbIndex owns object/path/reverse-use/affected-path indexing;
  GedEventTxn owns mutation batching, event coalescing, reconcile phases, and
  post-reconcile observer notification; GedDrawState owns retained draw
  intents, typed realized geometry, stale state, draw/erase/clear/redraw/who
  behavior, and shared/independent view transactions; GedSelectionState owns
  semantic selection and highlight synchronization.
* Do not recreate DbiState, BViewState, gedp->dbi_state,
  ged_dbi_state_*, include/ged/dbi_state.h, src/libged/dbi.h, or
  src/libged/dbi_state.cpp as the ownership model.
* Modern drawing publication is typed: line sets, point sets, indexed line
  sets, indexed face sets, text, annotations, images, overlays, proxies, and
  edit previews.  Modern paths should not expose raw vlists/vlblocks or raw
  BSG internals.
* Observers should see stable post-reconcile state only.  Avoid notifying UI
  or application consumers while database, draw, selection, or edit state is
  partially mutated.
* Scale work should be bounded by affected objects, active draw intents,
  expanded Qt branches, selected/edit targets, and active views.  Full rebuilds
  are acceptable for open-file, explicit rebuild, corruption, batch import, or
  events whose scope cannot yet be localized.
* Avoid full path-string scans in hot update paths.  Prefer path hashes,
  reverse-use answers, affected-path hints, and loaded-row indexes.  If full
  path matching is unavoidable, benchmark it at scale and add a regression
  gate.

Obol prototype lessons:

* The prototype proved enough to proceed with Obol-canonical work: database
  source nodes, SoBRLRealizeAction, real librt/db_walk_tree traversal,
  combination instance transforms, SoBRLVListShape, SoBRLMeshShape, shaded
  ARB8/RPP/BoT realization, NMG tessellation fallback, pick details, snap,
  measure, export, draw-intent fields, edit preview, field-sensor
  invalidation, partial source refresh, scene-controller rebuild from existing
  Obol nodes, grid/axes/ADC overlays, direct Obol GL rendering, non-GL
  renderScene proof, NanoRT proof, readback, and Obol HUD use without libdm.
* Every new feature should first be expressed as normal Obol scene
  programming: node fields, field sensors/notification, actions, details,
  state/elements only where traversal state is genuinely needed, and
  application-owned backends through Obol's context/backend interface.
* Do not add a generic BRL-CAD node/field/action/render layer unless a
  concrete test shows Obol cannot represent the needed behavior cleanly.
* Continue the Obol pivot if libbrlobol remains a small BRL-CAD extension
  layer on top of Obol.  Pause and reconsider if libbrlobol starts exposing
  generic scene, field, render-item, or backend-adapter types that duplicate
  Obol.

LoD pipeline details:

* The source database is authoritative.  LoD data is disposable derived
  display/cache data.
* The staged service should produce metadata/dependency records, attributes
  and AABB, OBB or cheap proxy, fast display LoD, qualified high-quality LoD,
  and exact/full-detail fallback as separate revision-tagged results.
* Provider-neutral request keys should include database identity, source
  revision or content hash, object path/name, view/policy revision, draw mode,
  provider id/version, provider parameters, quality tier, bounds, primitive
  counts, estimated error where known, terminal/fallback status, and
  diagnostics.
* POP Buffer generation is the first production fast-BoT provider because it
  is robust for triangle soup and invalid BoTs.  Progressive mesh generation
  should be a later provider for qualified clean topology.
* The older cache_drawing.cpp experiment contributed useful shape: staged
  fast-to-slow workers, main-thread result queue, serialized cache writer,
  debug delay knobs, and AABB/OBB/LoD milestones.  Do not carry forward its
  detached workers, object-name-only keys, void* lifetime, fixed linear
  assumptions, or informal rt_db_internal ownership.
* concurrentqueue.h may be used for high-volume producer/consumer handoff if
  it improves implementation quality, but correctness must come from
  enqueue/dequeue success, cancellation/shutdown tokens, generation ids, and
  in-flight counts.  size_approx() is only diagnostic.
* Result-ready wakeups are signals only.  Workers publish BRLObolLodResult
  records and coalesced wakeups; the owning view/controller drains results on
  the UI/main thread and applies SoBRLLodUpdateAction to matching scene nodes.
* Large LoD-backed BoTs must avoid mandatory full-detail residency.  Exact
  operations should request source-backed whole-object reloads, bounded
  chunks, or bbox/intersection-targeted subsets through the RT/provider path.
* A POP-build spatial sidecar is plausible and should remain optional: while
  walking source triangles, assign faces to coarse normalized Morton/grid
  buckets, union leaf bboxes, store source face ids or ranges, and build a
  shallow tree.  It is useful only if paired with a BoT partial-read API or
  cached full-detail chunk provider.

Framebuffer and image-stream plan:

* Obol owns display, placement, layering, texture upload, readback, backend
  selection, window hosting, and input integration.
* libimgstream owns mutable streams, pixel storage, dimensions, dirty
  rectangles, generation counters, clear/read/write/read-rect/write-rect,
  snapshots, producers, subscribers, fan-out, in-memory streams, file
  sinks/sources, transport, fb compatibility, null/debug/txt diagnostics, and
  fbserv/remrt/rt workflows during migration.
* libicv owns static image containers, codecs, file I/O, image transforms, and
  neutral colormap/lookup-table operations.
* fb compatibility lives inside libimgstream as fb_compat.h/fb_compat.c unless
  implementation evidence justifies a split.
* Preserve useful transport mechanisms: host:port, ipc:<addr>, PKG_ADDR
  handoff, FBSERV_TOKEN, FBSERV_TLS, and MSG_FB* where needed.
* Treat legacy view, cursor, poll, expose/resize, linger, simple mouse, and
  pan/zoom behavior as compatibility/display state.  Do not let it define the
  core image-stream API.
* Device spelling maps under compatibility: /dev/mem becomes in-memory stream
  behavior; /dev/disk becomes file sink/source behavior; /dev/stack becomes
  fan-out; /dev/null, /dev/debug, and /dev/txt become diagnostic sinks;
  remote, host:port, tcp:, and ipc: spellings become transport endpoints;
  display specifiers such as /dev/qtgl, /dev/ogl, /dev/wgl, /dev/X, and
  /dev/swrast request display through an active Obol/libbrlobol host or fail
  explicitly when no host exists.
* The libbrlobol window-host contract should hide toolkit details.  Qt, Tk,
  GLX/WGL, and other native handles belong in adapter-private code or explicit
  application integration hooks.  Long-term input bindings should be semantic,
  not Tcl strings, although the Tk adapter may translate legacy Tcl bindings
  during migration.

Performance Gates
-----------------

Before final BSG/DM removal:

* Initial realization/render on selected regression models should be within
  25 percent of the current path, or have an explicit documented and accepted
  reason.
* Camera-only redraw and selection/pick updates should be equal or faster
  than the old path on the selected regression models.
* Small imports and small hierarchy updates must not show pathological
  scaling.
* regress-gqa should remain a sub-second test unless the test scope is
  deliberately expanded.


Open Questions
--------------

* Which Obol upstream APIs need to be added or improved once qtcad uses Obol
  as the visible renderer?  This needs more implementation evidence and
  discussion before turning into concrete migration tasks.

Resolved decisions:

* plot3 should gain a normal libbg implementation unit; plot3.h is unlikely to
  be retired.
* bg_line_layer-to-plot3 export should remain available as a simple diagnostic
  output path for debugging without requiring Obol execution.
* MGED should target a proper Tcl/Tk Obol widget for performant native
  rendering when system OpenGL/Vulkan/etc. are available; OSMesa/offscreen
  rendering plus image presentation remains a slower fallback.
* Residual libdm framebuffer behavior should split as described in
  the framebuffer plan: libimgstream for mutable streams, producer/subscriber state,
  transport, fbserv behavior, and fb compatibility; libicv for static images,
  codecs, and lookup-table image transforms; Obol/libbrlobol for image
  display, texture nodes, readback, display-host callbacks, and window/input
  hosting.


Final Completion Criteria
-------------------------

The migration is complete when:

* Obol is the only scene/rendering API used by BRL-CAD interactive
  applications.
* qged/qtcad and mged pass their Obol display workflows.
* libbsg, libdm, and dm_plugins are absent from build, install, public
  headers, pkg-config files, and linked target graphs.
* libbrlobol remains BRL-specific and does not contain a generic BSG
  replacement.
* Documentation names Obol as the canonical scene API and explains where
  BRL-CAD Obol extensions live.
