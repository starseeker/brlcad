BRL-CAD Obol Active Work Guide
==============================

Last refreshed: 2026-07-02

Purpose
-------

This is the first file a new or resumed AI session should read before working
on the Obol migration.  It is intentionally current and action-oriented.
Use `obol_worklog.txt` for detailed history, rationale, and older verification
records.  Use `doc/notes/obol_legacy_dependency_inventory.txt` for the guarded
dependency rows and phase ownership notes.


Working Rules
-------------

* Work on the oboltest branch unless the user redirects.
* Do not rebase oboltest again unless the user explicitly asks.
* Primary BRL-CAD build directory is `build/` and uses Ninja.
* If modifying embedded Obol sources, build in `obol/build` and run install so
  BRL-CAD CMake can detect the staged update.
* The compile/test cycle is slow.  Batch low-risk related changes when root
  causing failures will still be straightforward.
* Keep Obol-canonical code free of new public BSG/libdm dependencies.
* Preserve user and existing worktree changes.  Do not revert unrelated edits.
* Keep `/tmp` clean.  This is a shared machine.
* Single tests over 180 seconds are a problem to investigate or split.
* Avoid premature profiling work during migration unless a change introduces a
  catastrophic slowdown.
* Update this file when active priorities, percentages, remaining blockers, or
  verification baselines materially change.


Migration Intent
----------------

BRL-CAD should use Obol as the canonical scene, view, interaction, and
rendering API for interactive 3D applications.

The migration is now Obol-primary for database draw ownership.  The old
parallel-first strategy produced too much sync/fallback ambiguity for
scene/source migration.  Database draw, erase, redraw, visibility, material,
path-state, bounds, and scene-record behavior should use Obol/libbrlobol as
the active owner; missing behavior should be fixed in Obol or exposed by
focused tests, not hidden behind retained BSG fallback.

Retained BSG/DM code may remain compiled as legacy/reference code while the
transition is underway.  The former temporary islands should be treated as
Obol node/store families to stand up as scope allows: overlays, qray/NIRT
uplot import, vdraw/local helper artifacts, annotations, feature/polygon/
selection stores, and the display stream.  If one of those families still uses
legacy code during the transition, that is scheduling only, not an active
fallback design.

libbrlobol is the BRL-CAD-specific Obol extension library.  It should define
BRL-CAD Obol nodes, actions, details, and narrow application services.  It
must not become a generic replacement for BSG's render-item/backend-scene
model.
