BRL-CAD POP Mesh LoD and Obol Integration Assessment
====================================================

Context
-------

BRL-CAD currently has two mesh level-of-detail mechanisms relevant to BoT
drawing:

1. The viable production path in `src/libbsg/mesh_lod.cpp`, surfaced through
   `src/libbsg/lod.cpp` and now partly neutralized through `include/rt/view.h`
   and `src/librt/cache_lod.c`.

2. The older VDS code in `src/librt/vds`, which implements view-dependent
   hierarchical simplification but is currently not the production path and is
   believed to have detail-loss and maintainability issues.

The Obol migration is moving BRL-CAD drawing away from BSG/libdm toward Obol
plus a BRL-CAD-specific `src/libbrlobol` layer.  Large BoTs are one of the
pressure points for that migration: simply realizing full mesh arrays into
Obol fields makes large meshes untenable.


What obol_migration.txt Already Says
------------------------------------

`obol_migration.txt` already points in the right direction.

It states that `include/rt/view.h` owns neutral `rt_view_info` and
`rt_view_lod_settings` snapshots for plot, LoD realization, and indexed-face-set
callbacks.  It also says `include/rt/view.h` exposes mesh LoD cache access
through an opaque `rt_mesh_lod` handle rather than returning `bsg_mesh_lod`
directly.

The key migration note is:

    The current cache implementation remains BSG-backed internally, but RT now
    exposes neutral rt_mesh_lod_load_level, rt_mesh_lod_load_view, and
    rt_mesh_lod_data_get helpers for loading and inspecting cached mesh data
    without exposing the BSG container.

That is the correct boundary.  Obol/libbrlobol should depend on the neutral RT
mesh-LoD surface, not on BSG LoD structures or BSG scene traversal.


Current POP Mesh LoD Behavior
-----------------------------

The current production mesh LoD implementation is the POP-buffer code in
`src/libbsg/mesh_lod.cpp`.

Its useful properties are:

* It generates cached LoD data for BoT meshes.
* It stores cache state under a context keyed by database/name/hash.
* It can load an active level directly.
* It can choose a level from view size and LoD scale.
* It incrementally loads finer POP data when increasing detail.
* It trims POP data when decreasing detail.
* Above the POP threshold, it clears POP arrays and uses callbacks to access
  full-detail BoT data.
* It has a `shrink_memory()` path intended for clients that have consumed the
  active data, for example after uploading backend geometry.

The neutral wrapper is in `src/librt/cache_lod.c`:

* `db_mesh_lod_update(dbip, name)` generates or refreshes cache data.
* `db_mesh_lod_get(dbip, name)` returns an opaque `struct rt_mesh_lod *`.
* `rt_mesh_lod_load_level(lod, level, reset)` loads a requested level.
* `rt_mesh_lod_load_view(lod, info, reset)` chooses a level using
  `rt_view_info`.
* `rt_mesh_lod_data_get(lod, data)` returns borrowed active arrays.
* `rt_mesh_lod_destroy(lod)` releases the handle.

The borrowed-array rule matters.  `struct rt_mesh_lod_data` arrays are valid
until the LoD is reloaded or destroyed.  Obol code must either consume/copy
them immediately or keep level changes coordinated with node/backend resource
updates.


Current libbrlobol Mesh Path
----------------------------

The current `src/libbrlobol/database_source.cpp` mesh realization path expands
BoTs directly into `SoBRLMeshShape` fields:

* vertices are copied into `SoMFVec3f point`;
* faces are copied into `SoMFInt32 coordIndex`;
* rendering, picking, measuring, snapping, and export operate over those fields.

This is acceptable for small meshes and tests, but not for large production
BoTs.  It front-loads full mesh memory into the Obol scene and bypasses the
POP-buffer cache entirely.

`SoBRLMeshShape` already has useful BRL-CAD scene-state fields such as:

* `sourcePath`
* `sourceName`
* `sourceType`
* material and color fields
* visibility/selectability fields
* selected/highlighted/ghosted fields
* `lodPolicy`
* selected/highlighted primitive arrays

Those fields are the right place for persistent Obol scene state.  The large
mesh coordinate/index arrays should not necessarily be Obol fields for
LoD-backed production meshes.


Recommended Integration
-----------------------

The clean integration is:

    Obol view/controller
        -> libbrlobol builds rt_view_info from Obol camera, viewport, and LoD policy
            -> librt rt_mesh_lod API
                -> current POP-buffer implementation, BSG-backed internally for now
                    -> later moved out of libbsg behind the same RT API

libbrlobol should not call or include:

* `bsg_mesh_lod`
* `bsg_mesh_lod_context`
* `bsg_view`
* BSG LoD nodes
* BSG LoD source-policy callbacks
* BSG scene refs for LoD

libbrlobol should call only the neutral RT APIs:

* `db_mesh_lod_update`
* `db_mesh_lod_get`
* `rt_mesh_lod_load_level`
* `rt_mesh_lod_load_view`
* `rt_mesh_lod_data_get`
* `rt_mesh_lod_destroy`


Obol Node Shape
---------------

Do not port BSG LoD nodes wholesale into Obol.

The POP-buffer mesh path is not primarily "choose one of N pre-realized child
nodes."  It is an active mesh container with lazy loading, trimming, and
full-detail fallback.  Modeling it as a generic Obol child-switching LoD node
would either duplicate large geometry per level or force a hidden side channel
that recreates BSG-like behavior.

Use one of these two approaches:

1. Add a dedicated `SoBRLLodMeshShape`.

2. Extend `SoBRLMeshShape` with a separate LoD-backed storage mode.

The dedicated node is probably cleaner.  It can keep the existing
`SoBRLMeshShape` simple and let production large-BoT handling have explicit
lifetime and cache semantics.

A LoD-backed mesh shape should store persistent scene state as normal Obol
fields:

* database source identity/path/name
* draw-intent fields
* material/color fields
* visibility/selectability
* selection/highlight state
* LoD policy and optional forced level
* source/input/view revision fields as needed

The large active mesh data should be private transient storage owned by the
node, or by a small node-private object wrapping `rt_mesh_lod`.  It should not
be forced into `SoMFVec3f` and `SoMFInt32` fields for large LoD meshes unless
a particular action requires a temporary field-compatible representation.


Update/Render Flow
------------------

Add a narrow libbrlobol action or controller pass, for example:

    SoBRLMeshLodUpdateAction

Its job:

1. Traverse the Obol scene looking for LoD-backed mesh shapes.
2. Build an `rt_view_info` from the Obol camera, viewport, and LoD policy.
3. For each visible LoD mesh:
   * ensure its `rt_mesh_lod` handle exists;
   * call `rt_mesh_lod_load_view`;
   * call `rt_mesh_lod_data_get`;
   * update node-private active arrays or backend geometry only if the selected
     level changed or a reset was requested;
   * mark the Obol node/backend resource dirty using normal Obol notification.

The view controller should run this update before rendering when:

* camera size/zoom changes enough to affect LoD;
* viewport dimensions change;
* LoD policy fields change;
* a source is newly realized;
* the database object changes;
* a forced LoD level changes.

This keeps LoD selection as normal Obol scene/update behavior rather than a
hidden display-manager table.


Memory Management
-----------------

The POP-buffer implementation already has the right memory model internally:
incremental load when refining, trim when coarsening, full-detail callback when
above the POP threshold, and `shrink_memory()` after a client has consumed the
active arrays.

The neutral RT API is missing one important piece: memory shrink is not exposed
through `rt_mesh_lod`.

Add a neutral helper such as:

    RT_EXPORT extern int rt_mesh_lod_current_level(const struct rt_mesh_lod *lod);
    RT_EXPORT extern void rt_mesh_lod_memshrink(struct rt_mesh_lod *lod);

or a combined status/query API if more metadata is desired.

Then libbrlobol can:

* load a level;
* upload/update GL/NanoRT/backend resources;
* release active CPU-side POP arrays when no CPU traversal needs them;
* reload on demand for pick/snap/measure/export.

Actions that require CPU triangles need a clear rule:

* Render backend update can use active arrays and then shrink.
* Pick/snap/measure/export can reload the current level on demand.
* Full-fidelity export should request full detail explicitly rather than use
  whatever view-selected display level is currently active.


Picking, Snapping, Measuring, and Export
----------------------------------------

There are two different needs:

1. Display-level operations, where using the active LoD mesh is acceptable and
   often desirable for interactivity.

2. Exact/model operations, where full-detail BoT data is required.

Do not blur those semantics.  The Obol action APIs should either:

* document that they operate on display geometry, or
* expose a policy flag requesting full-detail reload/access.

For example:

* viewport pick can use active display LoD by default;
* precision measurement should be able to force full detail;
* export should default to full/detail-preserving output unless explicitly
  asked for display-LoD export;
* snap may need mode-specific behavior, because display snap is interactive
  while edit snap may need exact geometry.

The POP implementation's full-detail callback path is relevant here: above the
POP threshold it can point back to full BoT arrays.  libbrlobol should reach
that capability only through RT-level APIs, not by unwrapping BSG internals.


POP-Build Spatial Sidecar
-------------------------

A coarse exact-query sidecar can plausibly be generated during POP cache
creation, but it should remain a sibling provider payload rather than part of
the display POP buffer.  The POP build pass already has the source vertex/face
arrays, normalization bounds, per-triangle quantized coordinates, source face
ids, and first active POP level.  While that data is hot, a provider can assign
each source triangle once to a coarse normalized Morton/grid bucket, accumulate
real triangle bboxes into leaf bounds, and build a shallow leaf tree whose
leaves carry source face ranges or ids.

The sidecar should be intentionally coarse.  Its leaves only need to make a
query result small enough for later exact processing, not isolate individual
triangles.  Avoid duplicating triangles into many overlapped cells unless a
test model proves it is necessary; oversized triangles can live in overflow
leaves, and query results may include false positives.  The performance target
is one extra streaming pass or cheap work folded into the existing POP face
walk, compact records, and no effect on display LoD loading when the sidecar is
not requested.

This becomes an out-of-core win only if RT can use the resulting source face
ids to read BoT subsets or cached full-detail chunks.  Without that subset data
path, the sidecar is still useful for pruning after a full load, but it does not
solve the memory problem by itself.


Cache Ownership and Invalidation
--------------------------------

The LoD cache should remain database/RT-owned, not Obol-owned.

Recommended ownership:

* `struct db_i` owns the `rt_mesh_lod_context`, as it already does in
  `src/librt/cache_lod.c`.
* Obol nodes own only their active `rt_mesh_lod` handle or a lightweight
  reference object tied to a database object name.
* When a BoT changes, RT invalidates/regenerates cache data via
  `db_mesh_lod_update` or a future database event hook.
* Obol nodes are marked stale by normal source/database revision fields.

Avoid per-view or per-node duplicate cache contexts.  Multiple Obol views of
the same database should share the same RT/database LoD cache while maintaining
separate current active levels or backend resources as needed.


Relationship to Obol LoD
------------------------

If Obol has or grows a generic LoD system, use it for generic scene semantics:

* switching between authored representations;
* hiding/showing representation children;
* range-based or complexity-based scene traversal.

Do not make generic Obol LoD own BRL-CAD POP-buffer mesh residency.

The BRL-CAD mesh LoD case has domain-specific requirements:

* BoT database lookup;
* POP-buffer cache generation;
* borrowed array lifetimes;
* full-detail callback fallback;
* RT-level view metrics and policy;
* database invalidation;
* exact-vs-display geometry policy.

Those belong in librt plus libbrlobol, behind a narrow Obol node/action
surface.  Generic Obol LoD can still drive or annotate policy, but it should
not replace the RT mesh-LoD provider.


What to Do with VDS
-------------------

Do not integrate `src/librt/vds` into the production Obol path now.

The useful VDS ideas are:

* per-view dynamic refinement;
* hierarchical spatial clustering;
* fold/unfold traversal;
* potentially better local adaptation than whole-object discrete levels.

But the current VDS code has problems for this migration:

* it is old and not currently the viable production path;
* it uses global construction state;
* it has its own tree and triangle proxy model;
* it is not already wrapped by the neutral RT LoD API;
* historical experience suggests detail loss;
* integrating it directly into libbrlobol would create a second mesh-LoD
  architecture alongside POP.

Treat VDS as reference material or a future experimental provider.  If it is
revived, make it implement the same RT-level provider contract used by POP:

    db/object -> rt_mesh_lod handle -> load by view/level -> borrowed active arrays

Obol/libbrlobol should not know whether the provider is POP, VDS, or a future
simplifier.


Suggested Implementation Steps
------------------------------

1. Keep the current RT mesh-LoD facade as the public contract.

2. Add missing neutral APIs for current level/status and memory shrink.

3. Add a LoD-backed Obol mesh shape, preferably `SoBRLLodMeshShape`, or add a
   clearly separated LoD-backed mode to `SoBRLMeshShape`.

4. During database mesh realization, choose LoD-backed realization for BoTs
   above `rt_view_lod_bot_threshold` or another BRL-CAD policy threshold.
   Small BoTs can continue using direct `SoBRLMeshShape` field storage.

5. Add `SoBRLMeshLodUpdateAction` or equivalent controller logic that updates
   LoD-backed mesh nodes from `rt_view_info` before render.

6. Make render, pick, snap, measure, and export actions consciously choose
   display-level or full-detail geometry.

7. Add tests:
   * BoT above threshold realizes as LoD-backed shape.
   * View-size changes select different levels.
   * Active face counts increase with finer levels.
   * Render still works after memory shrink.
   * Pick/snap/measure can reload data after shrink.
   * Full-detail export does not accidentally export coarse display LoD.
   * Database change invalidates the cache and stale Obol node.
   * No libbrlobol code includes BSG LoD headers.

8. Later, move POP-buffer implementation out of libbsg behind the same RT API,
   or split it into a lower-level library used by librt.  The Obol-facing code
   should not change when that happens.


Bottom Line
-----------

Use the current POP-buffer mesh LoD method for production.  Integrate it with
Obol through the neutral `rt_mesh_lod` and `rt_view_info` APIs.  Add a
LoD-backed Obol mesh node/action path in libbrlobol that keeps persistent scene
state in Obol fields while keeping large active mesh arrays private and
reloadable.

Do not port BSG LoD nodes or policies into libbrlobol.  Do not wire VDS
directly into Obol.  VDS can inform future provider design, but production
should proceed with POP behind RT's opaque mesh-LoD contract.
