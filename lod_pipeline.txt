BRL-CAD LoD Pipeline Design Notes
=================================

Purpose
-------

This document sketches a proper BRL-CAD level-of-detail pipeline for the
Obol/libbrlobol display path.  The goal is not to preserve the current BSG LoD
implementation as-is, but to reuse its useful ideas and combine them with an
async staged cache model.

The core design principle is: show something useful quickly, then refine as
better cached data becomes available.

The source database remains authoritative.  LoD data is disposable derived
display/cache data.


High-Level Shape
----------------

LoD should be implemented as a provider-neutral realization service below
Obol/libbrlobol.  Obol should request realized geometry for a database path,
view state, draw mode, source revision, and LoD policy.  It should receive
immutable realized geometry handles and staged result notifications.

Obol nodes such as SoBRLDatabaseSource and SoBRLMeshShape should not know
whether geometry came from bounds, POP Buffers, progressive meshes, adaptive
primitive tessellation, or full-detail fallback.

The service should support these staged results:

  0. object metadata and hierarchy state
  1. attributes and AABB
  2. OBB or other cheap proxy
  3. fast display LoD
  4. qualified high-quality LoD
  5. exact/full-detail fallback


Staged Pipeline
---------------

Stage 0: Directory and dependency scan

  Build source records from db_i directory entries, object paths, source
  revisions, and tree dependencies.  This stage is enough to schedule work and
  associate later results with Obol database-source nodes.

Stage 1: Attributes and AABB

  Read display-relevant attributes such as region id, material/color, air code,
  LOS, inherit flag, and source type.  Compute or retrieve an AABB using the
  primitive bbox callbacks where available.

  This gives Obol a cheap placeholder and useful culling/picking data.

Stage 2: OBB or cheap proxy

  Compute oriented bounds or another low-cost proxy.  The older prototype used
  ft_oriented_bbox and stored an arb8-style OBB.  That is still a good
  intermediate display and selection candidate representation.

Stage 3: Fast display LoD

  For BoTs, generate or load POP Buffer data.  POP is the robust fast path: it
  assumes little about topology and can be prepared much faster than progressive
  mesh data.

  For native primitives, generate a coarse adaptive tessellation directly from
  the exact primitive instead of full tessellating and then simplifying.

Stage 4: Qualified high-quality LoD

  Analyze BoT topology.  If a BoT is clean enough, build a progressive mesh
  cache asynchronously.  Good candidates are manifold or boundary-manifold,
  consistently oriented, low in degenerates/duplicates, and either connected or
  decomposable into a small number of meaningful clean components.

  If the BoT is triangle soup, nonmanifold, badly oriented, or highly
  fragmented, mark POP as the terminal mesh LoD provider and do not repeatedly
  retry expensive progressive mesh preparation.

Stage 5: Full-detail fallback

  Load full BoT data or high-detail primitive tessellation only when needed:
  close views, exact picking, editing, export, still-frame refinement, or when
  no lower-level provider can satisfy the request.


Provider Policy
---------------

The pipeline should be provider-neutral.  Expected providers:

  assembly/proxy
      Uses hierarchy, object bounds, region state, and screen size to decide
      whether to skip, draw bounds/proxy, or expand children.

  primitive-adaptive
      Default for native CAD geometry.  Produces tessellation from exact
      sources using screen-space error and draw-mode policy.

  pop-buffer
      Default fast BoT provider and fallback for bad mesh topology.

  progressive-mesh
      High-quality BoT provider for clean mesh-like surfaces.  Should preserve
      sharp edges, boundaries, material regions, normals, and other available
      attributes where practical.  Supports geomorphing or selective refinement
      where the renderer can use it.

  full-detail
      Exact/high-detail provider used for editing, exact picking, and terminal
      fallback.


Concurrency Model
-----------------

The older cache_drawing.cpp prototype used a 5-stage concurrent pipeline:

  q_init  -> attr_worker
  q_aabb  -> aabb_worker
  q_obb   -> obb_worker
  q_lod   -> lod_worker
  q_write -> write_worker

It also used a results queue drained by the main thread.

That shape is worth preserving, but the production design should generalize it
from a fixed chain into a small task graph with dependencies.  Some work is
strictly ordered for one object, but different objects should advance
independently.

Use moodycamel::ConcurrentQueue from:

  src/libged/bot/concurrentqueue.h

This queue is useful for inter-stage producer/consumer handoff and for the
main-thread result queue.  The important guarantees we want are multi-producer,
multi-consumer, low-overhead enqueue/try_dequeue behavior without central
locking on every result handoff.

The implementation should still avoid relying on size_approx() for correctness.
It is appropriate for diagnostics, idle waits, and settled checks, but the real
logic should be driven by successful enqueue/dequeue operations, shutdown
tokens, generation ids, and explicit in-flight counters.


Persistent Cache Writes
-----------------------

The prototype used a single write_worker to serialize bu_cache/LMDB writes.
That is a good rule to keep unless bu_cache is changed to provide stronger
multi-writer guarantees.

Worker stages should enqueue cache write requests, and the writer should own
persistent writes and stale-entry clears.  This keeps compute stages from
blocking on LMDB write serialization.

Cache keys should not be based only on object names.  Use source revision,
content hash where needed, database identity, provider type, provider version,
and provider parameters.


Result Notifications
--------------------

The prototype posted DrawResult records for AABB, OBB, and LoD.  The new result
type should be provider-neutral and include:

  object path/name
  source revision token
  view/policy revision token when relevant
  result kind
  quality tier
  provider id
  cache key or realized geometry handle
  bounds
  triangle/point counts
  estimated error when known
  terminal/fallback status
  diagnostic text or code

Obol should drain results on the UI/main thread and apply only results whose
revision tokens still match the current source/view/policy.  Late results from
older revisions must be harmlessly ignored.


Ownership and Shutdown
----------------------

The prototype stored C++ pipeline state behind void* and detached worker
threads.  Production code should avoid that lifetime pattern.

Use an owned worker pool or owned task service with:

  explicit start/stop
  joinable shutdown
  cancellation tokens
  generation ids for stale work
  in-flight task counts
  bounded or priority-aware queues where needed

rt_db_internal ownership must be explicit.  If a cracked internal is passed
through stages, exactly one final owner must free it.  The prototype used the
LoD worker as the last consumer; that cleanup contract is useful, but should be
encoded in task ownership rather than informal comments.


Obol/libbrlobol Integration
---------------------------

SoBRLDatabaseSource should submit realization requests and accept staged
updates.  Its existing source/input/view revision fields are a good foundation.

SoBRLMeshShape should remain a display and picking node.  It should receive
stable geometry buffers and identity/material/picking metadata.  It should not
run LoD selection or know provider internals.

Obol should be able to display:

  AABB or OBB placeholder
  coarse proxy
  POP fast mesh
  progressive/high-quality mesh
  full-detail mesh

as later results arrive.

Selection, highlighting, editing, and exact picking should bias policy toward
higher-quality or full-detail realization.

CSG implicit solids and implicit-solid-backed comb instances are a different
case from mesh display picking.  Their exact pick path should convert the Obol
view ray into a librt ray query and return the nearest valid RT hit with
display instance path, region/material metadata, primitive identity, hit point,
normal, and distance.  Display tessellation or LoD proxies are useful for
interactive hover/display picking, but they should not be the authoritative
answer for exact implicit-solid selection.

For very large BoTs, exact picking or edit snapping should not require loading
the full mesh if a narrower query can identify a small working set.  A useful
optional provider capability would be a persistent spatial/index sidecar: for
example, a BVH/kd-tree/cluster tree whose leaves record triangle index ranges
or explicit triangle ids.  Exact operations could intersect the tree first,
then request only the candidate triangle spans from the RT/database provider.
This is only worthwhile if librt can expose a clean BoT partial-read API
backed by usable offset/index metadata; otherwise the first production fallback
should remain whole-object reload or coarser chunk reload behind the same
provider contract.

The POP build pass is a plausible place to emit the first coarse spatial
sidecar because it already streams the full source triangles, computes the
normalization bounds, assigns each triangle a first active POP level, and keeps
source face ids while filling the per-level buckets.  That is enough to build a
cheap sibling index without making POP itself a query structure: compute each
source triangle bbox or centroid during the POP face walk, assign each triangle
once to a coarse normalized Morton/grid bucket, union real triangle bboxes into
leaf bounds, and build a shallow upper tree over those leaves.  Leaves should
target a face/byte budget large enough that the tree stays coarse; they only
need to identify tractable source-face ranges or ids for a later provider query,
not per-triangle BVH leaves.  Large triangles can go to overflow leaves, and
queries may return extra faces as long as they do not miss.  Keep this sidecar
optional and cached next to the POP payload; do not require it for display
payload loading, and do not hold it resident in Obol nodes except through an
RT/provider handle.  It becomes valuable only when paired with BoT subset reads
or cached full-detail chunks; without that backing path it is still useful as
a pruning record after a full load, but it does not solve out-of-core exact
operations.


Lessons From Existing Code
--------------------------

Reuse from src/libbsg/mesh_lod.cpp:

  content-hash style cache identity
  POP Buffer fast preparation
  level-chunked cached data
  full-detail callback/fallback concept
  memory shrink/reload behavior
  spatial/index sidecar concepts if they can support targeted exact reads

Reuse from src/librt/vds:

  view-dependent refinement as an architectural idea
  fold/unfold/refine/coarsen policy concepts

Reuse from https://github.com/hhoppe/Mesh-processing-library:

  progressive mesh vertex-split representation
  geomorphing
  selective view-dependent refinement
  attribute-aware simplification
  terrain tiling and stitching ideas

Reuse from the older cache_drawing.cpp prototype:

  staged fast-to-slow preparation
  result queue drained by main thread
  serialized cache writer
  debug delay knobs for observing intermediate stages
  explicit AABB/OBB/LoD result milestones

Avoid carrying forward:

  BSG-specific pipeline APIs
  object-name-only cache keys
  detached unmanaged workers
  C++ implementation details exposed through librt_private.h
  fixed linear pipeline assumptions where a task graph is needed


Recommended Build-Out Order
---------------------------

1. Define provider-neutral request/result/handle types.
2. Add async realization service with owned workers and result queue.
3. Wire Obol to consume staged results while initially preserving existing mesh
   and wireframe realization behavior.
4. Add Stage 1/2 cache outputs: attributes, AABB, OBB/proxy.
5. Move POP generation behind the provider interface as Stage 3.
6. Add BoT topology qualification.
7. Add progressive mesh cache generation for qualified BoTs as Stage 4.
8. Add cancellation, priorities, still-frame refinement, and component-level
   progressive mesh handling.
