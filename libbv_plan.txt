BRL-CAD libbv Refactor Plan
===========================

Last refreshed: 2026-07-08

Purpose
-------

libbv is BRL-CAD's scene-graph-free view mechanics library.  It keeps the
useful idea of a shared view layer without preserving the old libbv API, the
historical bview data model, or the temporary BSG scene ownership model.

The intended split is:

* libbv owns passive, display-independent view state and view math.
* libbrlobol/Obol owns scene objects, visualization realization, interaction
  objects, picking, selection, command visuals, framebuffer presentation, and
  view-aware LoD realization.
* librt owns geometry/evaluation algorithms.  It should not retain
  application scene state.
* libged, qtcad, MGED, and GSH own application policy and host integration.

Current Boundary Decision
-------------------------

libbv should contain data and algorithms that remain valid without a database,
display manager, framebuffer server, Obol scene, Coin node, Tcl interpreter, or
application command context.  If a feature needs a scene object, a database path,
a display window, or a command policy decision, it is not a libbv feature.

libbv Owns Now
--------------

The current `struct bv` already has the right core shape:

* view/camera state and view sets.
* view dimensions, scale, size, perspective, unit conversion, z clipping, and
  frame bookkeeping.
* model2view, view2model, pmodel2view, pmat, rotation, and center matrices.
* eye, aet, keypoint, current point, mouse state, and generic view-adjust state.
* screen/view/model coordinate conversion and plane helpers.
* autoview from explicit bounds.
* generic knob state and knob command interpretation.
* display-independent refresh/dirty counters, frame time, framebuffer mode,
  cleared state, and opaque host user data.

Good Next libbv Candidates
--------------------------

The remaining useful libbv candidates are passive per-view data records:

* Faceplate and overlay state records: grid, ADC, model axes, view axes, center
  dot, scale overlay, parameter display, and interactive rectangle state.
  These belong in libbv only as data plus display-independent defaults and
  validation.  Rendering those records as Obol/Coin nodes remains
  libbrlobol/Obol work.
* Snap preferences: line snapping enabled/disabled, snap source flags, snap kind
  masks, and snap tolerance factors can live in libbv as per-view user
  preferences.  Snap candidate generation from database geometry, polygons,
  features, or scene objects remains libbrlobol/libged/qtcad work.
* View-set lifecycle and bookkeeping refinements that make multi-view sharing
  simpler without adding scene ownership.

Target Context Shape
--------------------

`rt_view_context_native` should not survive as a renamed RT wrapper.  The target
is a real libbv context, either `struct bv` if the current object remains
sufficient or a small `struct bv_context` if grouping view mechanics, passive
overlay records, snap preferences, and view-set membership behind one type makes
call sites clearer.

That libbv context should be usable directly by librt algorithms, libged, qtcad,
MGED, GSH, and libbrlobol without carrying retained scene state.  Code that
needs scene state should hold a libbv context plus an owner-specific companion
object, not extend libbv to become a scene facade.

Destination Map for Non-libbv State
-----------------------------------

The non-libbv fields currently mixed into `rt_view_context_native` should move
to their natural owners:

* Display-manager pointers, framebuffer/window handles, and headless backend
  attachment state move to the application/view host layer: MGED, GSH, qtcad,
  and libged-facing host objects.
* TclCAD data moves to libtclcad/MGED command integration state.
* Callback tables, update hooks, redraw scheduling, and application event
  integration move to the application/view host layer.  libbrlobol may expose
  scene/cache change notifications, but the host decides how to schedule redraws.
* Edit matrices and edit-preview behavior move to the modern editing stack:
  librt edit operations and math, libged/MGED/qtcad command policy, and
  libbrlobol/Obol preview/manipulator visualization.
* Scene root refs, independent scene scopes, shared scene handles, and per-view
  overlay roots move to libbrlobol/Obol view attachment state.
* LoD policy, cache advancement callbacks, and per-view LoD realization move to
  libbrlobol/Obol view state.  If a future generic "quality preference" is
  useful, it can be a passive libbv preference, but not the realization logic.
* Selection, picking, feature, and polygon adapters move to libbrlobol/Obol plus
  libged/qtcad command policy.
* Snap solving and snap candidate construction move to libbrlobol/libged/qtcad.
  Only passive snap preferences are libbv candidates.

Keep Out of libbv
-----------------

Do not move these into libbv:

* Obol/Coin nodes, scene refs, independent scene scopes, CAD packets, or source
  publication.
* Database sources, display lists, drawable geometry, or command visualization
  objects.
* Selection state, picking results, feature stores, polygon stores, or polygon
  editing behavior.
* Actual snap candidate construction or snap hit testing against scene/database
  content.
* LoD payloads, LoD caches, cache-population workers, and per-view LoD scene
  realization.  A future generic view-quality preference could be libbv data,
  but current LoD policy drives libbrlobol/Obol rendering and should stay out
  of libbv.
* Edit preview/manipulator state.  Editing should use librt edit operations,
  libged/MGED/qtcad policy, and libbrlobol/Obol manipulators.  libbv supplies
  view math snapshots only.
* Display-manager pointers, TclCAD data, callbacks, update hooks, display
  windows, framebuffer protocol handling, Auth/TLS, or fbserv wire logic.
* Compatibility surfaces whose only purpose is preserving retained BSG behavior.

Current Code State
------------------

Implemented libbv core:

* `include/bv.h`
* `include/bv/view.h`
* `src/libbv/view.c`
* `src/libbv/tests/view.c`

Current transitional state:

* `src/librt/view_context_native.c` embeds `struct bv` and delegates core view
  mechanics to `bv_*`.
* `rt_view_context_native` still stores several fields that should not stay
  there long term: display manager/TclCAD/callback host fields, edit matrix,
  scene root and independent scope refs, LoD policy state, faceplate/overlay
  records, and snap preferences.
* Neutral `rt_view_scene_ref` helpers are separate from the BSG adapter path.
  They are still migration scaffolding, not a reason for librt to own a scene.
* The sketch polygon BSG adapter path has been retired.  Remaining polygon
  handling should stay on native/Obol adapter paths and then move out of the
  generic RT view facade as callers are cleaned up.
* `include/rt/view_legacy_bsg.h` and `src/librt/view_legacy_bsg.c` are legacy
  removal targets, not design references.

Migration Plan
--------------

1. Add libbv-owned passive faceplate/overlay records and accessors, with
   display-independent defaults matching current native RT defaults.
2. Add libbv-owned snap preference records if qtcad/MGED/GSH need shared
   behavior.  Keep snap solving outside libbv.
3. Decide whether `struct bv` remains the public context or whether to introduce
   `struct bv_context` as a thin libbv grouping type.  Do not base this on the
   existing RT wrapper layout.
4. Retarget native `rt_view_context_*` faceplate/snap accessors to delegate to
   libbv, then migrate production callers to direct `bv_*` or libbrlobol APIs.
5. Move display manager, TclCAD pointers, callbacks, and update hooks into
   their actual application/view host owners.
6. Move scene root, independent scope, feature, polygon, selection, picking,
   and LoD realization APIs to libbrlobol/Obol-facing ownership, or delete
   them where they only support BSG compatibility.
7. Delete `rt_view_context_native` once its remaining state has a libbv,
   libbrlobol, application-host, or deleted destination.
8. Delete BSG-specific constructors, wrappers, tests, and headers once no
   production caller needs them.
9. Keep libbv tests focused on pure view mechanics and passive per-view data.
   Test scene realization, picking, selection, LoD, and framebuffer behavior in
   libbrlobol/libged/qtcad/MGED/GSH tests.
