Working Rules
-------------

* Work on the oboltest branch unless the user redirects.
* Do not rebase oboltest again unless the user explicitly asks.
* Primary BRL-CAD build directory is build/ and uses Ninja.
* If modifying embedded Obol sources, build in obol/build and run install so
  BRL-CAD CMake can detect the staged update.
* The compile/test cycle is slow.  Batch low-risk related changes when root
  causing failures will still be straightforward.
* Keep all Obol-canonical code free of new public BSG/libdm dependencies.
* Preserve user and existing worktree changes.  Do not revert unrelated edits.
* Update this file when the active work queue, percentages, or next-step
  priorities materially change.  Put longer rationale in obol_worklog.txt.


Migration Intent
----------------

BRL-CAD should use Obol as the canonical scene, view, interaction, and
rendering API for interactive 3D applications.

The migration is parallel-first: build the Obol path beside the current
BSG/DM path until it reaches production parity, then remove public libbsg,
libdm, dm_plugins, and BSG/DM-shaped application APIs.  Temporary internal
bridges are acceptable while a phase is incomplete.  No long-lived public BSG
or DM compatibility layer is part of the target design.

libbrlobol is the BRL-CAD-specific Obol extension library.  It should define
BRL-CAD Obol nodes, actions, details, and narrow application services.  It
must not become a generic replacement for BSG's render-item/backend-scene
model.

The first production target is qged/qtcad.  After qged is usable on Obol,
migrate GED/TclCAD/mged, then remove lower-level BSG/DM utility dependencies.

Decisions That Should Guide New Work
------------------------------------

* Obol cameras, transforms, SoViewport, SoRenderManager, actions, nodes,
  fields, and details are authoritative for scene, view, render, and
  interaction state.
* New drawing code should use Obol directly or use BRL-CAD Obol extensions.
  Do not add new BSG/DM dependencies outside explicit legacy allowlists.
* C and Tcl callers may use opaque bridges backed by Obol; C++ is acceptable
  for code directly interacting with the drawing API.
* bg_vlist and bg_line_layer are low-level geometry/debug containers, not
  scene APIs.  Application-visible drawing state should be Obol nodes.
* libbg should gain normal implementation units for neutral plot/debug
  helpers.  plot3.h is unlikely to be retired.
* Keep the bg_line_layer-to-plot3 diagnostic path.  It is useful for simple
  debugging output and should not require Obol execution.
* Scene text, labels, HUD text, and annotations should use Obol 2D/3D text.
  Flattened text geometry should be generated from an Obol-backed path when
  export requires it.
* MGED should target a proper Tcl/Tk Obol widget for performant native
  rendering when system OpenGL/Vulkan/etc. are available.  OSMesa/offscreen
  rendering plus image presentation is a slower fallback, not the target.
* Obol owns image display, placement, layering, texture upload, readback, and
  rendering backend selection.
* libimgstream owns live mutable image streams, async image producers,
  dirty-update notification, transport, fan-out, fbserv compatibility, and
  fb_* wrappers during migration.
* libicv owns static image containers, codecs, image file I/O, image
  transforms, and neutral colormap/lookup-table operations.

   stronger provider/policy scheduling, and caller integration for exact

   qtcad has the first source-backed mesh and database-source RT exact pick
   paths.  Remaining work is wiring non-qtcad callers to the shared helpers
   and carrying the same display/source/RT duplicate-suppression policy into
   those tools.

5. Make qtcad visibly render through Obol by default.

   qtcad needs Obol visible paint, navigation, autoview, selection, picking,
   snapping, measuring, overlays, edit preview, and screenshot/readback to work
   for real .g workflows without requiring libdm for migrated content.

6. Replace diagnostic publication with Obol overlays.

   Define Obol-side lines, points, labels, axes, grids, faceplate/HUD, edit
   previews, and selectable diagnostics.  Keep bg_line_layer as a neutral
   producer/container and keep plot3 export as a simple diagnostic output path.

7. Continue libimgstream/fb display ownership migration.

   Route display-capable framebuffer requests through registered Obol
   display/window hosts.  Add dirty-region texture uploads, broader dm_open
   routing, hardware-preferred Qt host selection, and Tk/MGED adapters.

   Keep the pivot guard and inventory current as each boundary migrates.  Do
   not weaken the existing behavior-specific checks; consolidate repetitive
   text scans only when the replacement preserves the same regression signal.
   A compiled scanner is acceptable for repetitive file/token checks if CMake
   scan time becomes the bottleneck, but avoid reimplementing complex semantic
   guard logic prematurely.

Large-Geometry LoD Policy
-------------------------

Do not design large BoT LoD around "preserve full detail in memory plus LoD".
That works only as an interim correctness bridge for already-resident meshes.

For very large geometry, including pathological cases like many Lucy-size mesh
primitives, the intended behavior is:

* Scene nodes keep source identity, display policy, bounds, counts, and the
  current display payload.
* Full-detail arrays are not required to remain resident.
* Exact operations fetch data from the authoritative .g/librt source when
  needed.
* If whole-object detail reload is too large, use chunks, bbox-targeted reads,
  or intersection-targeted reads behind the provider contract.
* A cached coarse sidecar can help exact pick/snap by mapping spatial leaves
  to source face ids or ranges, but it only pays off when librt can actually
  provide partial BoT reads or cached full-detail chunks.

The POP build pass is a plausible place to emit that sidecar because it already
walks source triangles, normalizes bounds, assigns active levels, and tracks
source face ids.  Keep the sidecar optional and coarse; it should not slow the
display POP path enough to hurt the main LoD benefit.

Open Questions
--------------

* Which Obol upstream APIs need to be added or improved once qtcad uses Obol
  as the visible renderer?  This needs more implementation evidence.
* Which residual libdm behaviors survive only as compatibility spelling, and
  which should be deleted after libimgstream/display-host replacement?  The
  main ownership split is recorded, but final behavior needs review as callers
  migrate.
* How much BoT subset-read/index-sidecar complexity is justified for exact
  queries?  Evaluate after the first source-backed full-detail provider path
  exists.


Final Done Criteria
-------------------

The migration is complete when:

* Obol is the only scene/rendering API used by BRL-CAD interactive
  applications.
* qged/qtcad and mged pass their Obol display workflows.
* libbsg, libdm, and dm_plugins are absent from build, install, public
  headers, pkg-config files, and linked target graphs.
* libbrlobol remains BRL-specific and does not contain a generic BSG
  replacement.
* Documentation names Obol as the canonical scene API and explains where
  BRL-CAD Obol extensions live.
