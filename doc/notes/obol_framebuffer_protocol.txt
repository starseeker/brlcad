Obol Framebuffer Protocol Boundary
==================================

Status
------

The fbserv wire-protocol transport currently lives in libdm because
historical embedded framebuffer users reached it through display managers and
`struct fb`.  That location is transitional.  The backend framebuffer
operation contract and transitional server object/transport type contract now
live in `include/imgstream/fbserv.h`, and new code should treat fbserv as a
framebuffer/image-stream protocol, not as display-manager or scene-graph
behavior.  The wire-protocol message IDs also live in
`include/imgstream/fbserv.h`, with legacy `MSG_*` aliases preserved for
existing fbserv callers.  Session-token authentication generation and
verification are compiled in libimgstream as shared fbserv protocol support.
Non-I/O object state helpers are also implemented in libimgstream, while
libdm keeps compatibility wrappers around those helpers until the packet loop
moves.  The libpkg PKG message switch is image-stream-owned and shared by
libdm and the standalone `fbserv` executable; the TCP/IPC event loops and
packet handler bodies remain transitional host code.  Backend-operation
dispatch through `struct fbserv_fb_ops` is also image-stream-owned; libdm
performs only the remaining legacy `struct fb` fallback when an operation is
not handled by an installed backend.

Target Ownership
----------------

Long term, protocol parsing and transport handling should move to a small
framebuffer-stream layer beside libimgstream/libicv.  Possible names include a
standalone `libfbserv` or a libimgstream protocol module.  The important
boundary is:

* Protocol layer: owns TCP/IPC packet handling, fbserv compatibility commands,
  stream dimensions, pixel writes/reads, colormaps, cursor/view compatibility
  state, and backend-neutral operation dispatch.
* libimgstream/libicv: own concrete image buffer storage, pixel formats,
  conversion, import/export, image-stream primitives, and the
  backend-neutral fbserv framebuffer operation contract.
* libbrlobol: owns Obol/Coin presentation of image streams, scene placement,
  view-local roots, render scheduling, pick/interaction behavior, selection
  metadata, and lifecycle inside BRL-CAD scenes.  The reusable
  `BRLObolFramebufferStream` helper owns the common image-stream-to-window-host
  lifecycle for memory-backed embedded framebuffer streams.

libbrlobol should not own fbserv packet parsing or `struct fb` compatibility.
Keeping that boundary clean avoids replacing one legacy display-manager
coupling with a scene-graph coupling.

Current Bridge
--------------

The current libdm fbserv implementation has a backend operation table and
transitional server object whose types and message IDs are declared by
`include/imgstream/fbserv.h`.  If a host installs the table, protocol handlers
call those operations; otherwise the legacy `struct fb` functions remain the
fallback backend.  This lets migrated applications prove Obol/imgstream
framebuffer behavior before the packet transport is physically moved out of
libdm.  Object initialization, backend/transport setup, listener/client state
accessors, and legacy framebuffer pointer attachment are image-stream-owned
helper implementations exposed through libdm compatibility wrappers.  The
PKG message-type dispatch table is also image-stream-owned, with libdm
supplying the current handler callbacks until those handlers are split from
the legacy `struct fb` fallback.  The handlers already call through
libimgstream backend-operation dispatch before reaching libdm's legacy
fallback path.

qged, libged, and TclCAD do not mutate `fbserv_obj::fbs_fbp` directly.
Obol-backed paths install an image-stream backend, and the remaining non-Obol
legacy fallback is attached or read through `fbs_set_legacy_framebuffer` /
`fbs_legacy_framebuffer` while the packet transport is still hosted by libdm.
TclCAD's older framebuffer-object commands still operate on a legacy
`struct fb` compatibility object, but they reach it through the fbserv
accessor boundary until that command surface is retired or wrapped separately.

libged and GSH also avoid direct fbserv transport internals.  They use narrow
`fbs_*` helpers for newly allocated object initialization, transport handler
install/clear, IPC/TCP capability checks, listener-port lookup, watcher
client-data access, IPC-client cleanup, and shutdown checks.  qged and TclCAD
still own their toolkit-specific socket/notifier/channel integration until the
packet transport is moved out of libdm, but that integration now uses narrow
`fbs_*` listener/client helpers instead of direct fbserv field access.

qged and TclCAD setup paths install transport callbacks through tables rather
than assigning individual `fbserv_obj` callback fields.  qged uses
`fbs_set_transport`; TclCAD uses `tclcad_fbserv_set_transport`, which selects
the platform-appropriate TCP/IPC handlers in one place.

Migrations should also use `fbs_framebuffer_*` operation wrappers to exercise
framebuffer behavior instead of reaching through `fbserv_obj::fbs_fb_ops` and
`fbs_fb_ctx`.  The backend table is an implementation detail while fbserv is
still hosted in libdm.

qged uses this path today through the shared libged Obol fbserv backend.  qged
supplies Qt socket/notifier transport, active `QgView` render sizing, a
borrowed `QgObolWindowHost`, and view refresh notification; libged supplies the
backend operation table that delegates pixel, view, cursor, colormap, flush,
and poll behavior to `BRLObolFramebufferStream`.  qged no longer selects
between qtcad GL and swrast framebuffer canvases for embedded framebuffer
traffic and no longer carries a second operation-table adapter.

GSH, classic MGED, and other non-Qt GED hosts use a libged Obol fbserv bridge
when an Obol DM is attached and no application-specific fbserv backend is
installed.  That bridge uses the same `BRLObolFramebufferStream` helper, owns
the generic fbserv watcher threads, and exposes an application update hook,
`ged_draw_obol_framebuffer_present`, so framebuffer stream state can be
published to the Obol scene before rendering.  The bridge is intentionally not
a new libdm framebuffer implementation; it is a transitional owner for the
protocol-to-imgstream path until fbserv moves out of libdm.

Current automated coverage includes `test_qged_obol_fbserv`,
`gsh_obol_smoke`, `gsh_obol_ert_smoke`, and `mged_obol_ert_smoke`.  These
prove the qged Qt-hosted shared-backend path and the plain GED Obol bridge can
attach, publish framebuffer state, present pending updates, launch real `ert`
subprocesses through the Obol IPC framebuffer path, and render through attached
Obol views.

The remaining coverage gap is a bounded slow streaming-image test that captures
intermediate framebuffer states rather than only the final/presented state.
In the current build, `NIST_MBE_PMI_3.g` is an empty 104-byte database because
the STEP conversion target is unavailable.  `NIST_MBE_PMI_7-10.g` can produce
distinct intermediate Obol framebuffer screenshots during a single-threaded
`ert`, but setup/runtime is too long for the default smoke suite.  Treat that
as manual/slow regression material until a shorter deterministic fixture or
explicit slow-test gate exists.

Threading Contract
------------------

Framebuffer producers may run on network/pkg watcher threads.  Those threads
may update `imgstream` pixel data, fb-compatible cursor/view state, dirty
metadata, and generation counters, but they must not mutate Coin/Obol scene
graph fields or rebuild geometry.

`SoBRLImageSource` therefore treats stream notification as a pending-update
marker only.  Its dirty callback records an atomic pending generation and does
not write Inventor fields.  The update owner calls `refreshFromStream`,
`SoBRLViewportImage::syncFromSource`, or `BRLObolFramebufferStream::present`
to copy coherent stream state into Coin fields and texture geometry.

The render traversal is read-only with respect to framebuffer scene state.
Applications must serialize their own update/present phase before render.
For qged, the Qt socket/notifier callback is the update phase and uses the
shared libged backend in UI-thread present-on-flush mode before requesting a
view refresh.  For GSH, the command-thread delay pump owns update/render in the
headless smoke path; the main subprocess-output loop does not render because
the dm-obol OSMesa renderer is thread-affine in that configuration.  Classic
MGED and TclCAD present pending Obol framebuffer state from their view refresh
paths before `dm_draw_begin`, keeping `ert` and other embedded framebuffer
producers dirty-only until the application update phase.

Design Implications
-------------------

* New framebuffer work should target the `include/imgstream/fbserv.h`
  backend operation table, server object/transport types, message IDs, and
  authentication and PKG switch helpers, not raw `struct fb`,
  display-manager internals, or legacy qtcad canvas lookup.
* Migrated hosts should use the `fbs_*` legacy-framebuffer accessors when they
  must attach a non-Obol `struct fb` fallback; direct `fbserv_obj::fbs_fbp`
  access remains transitional legacy code, not the model for new callers.
* Migrated hosts should use the `fbs_*` transport/accessor helpers rather
  than reading listener slots, client slots, or transport callbacks directly.
  Toolkit hosts may still own event-loop wiring during the transition, but
  should route listener/client state through the helper APIs.
* Toolkit hosts should install callback tables through `fbs_set_transport`
  (or host-owned wrappers such as `tclcad_fbserv_set_transport`) rather than
  assigning fbserv callback fields piecemeal.
* Callers should use `fbs_framebuffer_*` helpers for backend operations rather
  than dereferencing `fbserv_obj::fbs_fb_ops` / `fbs_fb_ctx` directly.
* Obol hosts should expose framebuffer content as scene objects or view-local
  presentation roots over image streams through `BRLObolFramebufferStream`.
* Legacy `struct fb` display devices should first try a registered imgstream
  display host.  `/dev/qtgl` and `/dev/swrast` now use that path for
  standalone `fb_open` calls when a host is registered, and only fall back to
  nested qtcad/libdm window creation when no host is available.
* Producer callbacks should publish dirty state only.  Coin field writes,
  geometry rebuilds, texture refresh, and render requests belong in an
  application/update phase, not in fbserv watcher threads or render traversal.
* MGED and GSH use the same pattern: attach an Obol view/controller, install an
  image-stream framebuffer backend, and verify raytrace updates appear in
  rendered screenshots.
* Once qged, GSH, MGED, and tests no longer need libdm's `struct fb` fallback,
  move the remaining packet transport beside libimgstream/libicv and shrink
  libdm.
