BRL-CAD Obol Overlay and Command-Result Coverage
================================================

Scope
-----

This note tracks Obol-side overlay and command-result representation.  The
neutral low-level diagnostic container is still `bg_line_layer`; libbrlobol
converts it to Obol/Coin scene objects only at publication boundaries.

----------------------------

Routed Producers
----------------

These producers currently publish through the command-scene path when an Obol
view exists:

* rtcheck uplot overlap lines as shared `rtcheck::` line layers.
* NIRT/qray plot lines as shared `query_ray` line layers.
* `check overlaps -o` lines and summary HUD labels as `check::overlaps`.
* GQA overlap, gap, adjacent-air, exposed-air, overlap-summary HUD, and
  opt-in dense volume-sample plot lines.
* GED `overlay` command uplot imports as shared `overlay::` line layers.
* `vdraw send` line, point, and indexed-face-compatible `_VDRW*` results.
* `gdiff`, `lint`, `joint`, `bot plot`, `bot_fuse`, `bot check`, and preview
  eye-path line visualizations.
* BREP debug line plots and NMG edge-use debug overlays.
* BREP debug indexed-face output, published as command-result indexed-face-set
  features.

The old private direct-uplot feature publishing wrappers are retired.  Uplot
producers should parse/build streams and publish through command-scene helpers;
without an active Obol feature store, overlay insertion returns no output and
does not recreate retained BSG overlay state.

The work grid is not modeled as transformed database-line geometry.  It is a
view aid owned by `SoBRLGrid`: visual lines are HUD overlay layers and grid
snap is semantic model/view state.  See `doc/notes/obol_grid_snap.txt`.

Fallback direct diagnostic callbacks remain only for non-command-scene
consumers that have not yet been migrated; they must not be used to preserve
parallel retained Obol/BSG ownership for migrated overlay producers.

Command-Result Contract
-----------------------

Command outputs such as NIRT rays, rtcheck overlap results, check overlaps, and
GQA diagnostics are scene objects, not passive decorations.  Their Obol
representation must be pickable, selectable, highlightable at primitive
granularity, and usable by snap/measure/export when the command declares those
semantics.

Commands should publish result sets with:

* owner id, owner role, and optional generation/run id
* shared scene scope by default, with explicit view-local opt-in
* replace/remove-prefix/commit lifecycle
* visible/selectable style
* stable feature id plus per-primitive indices
* feature metadata and per-primitive metadata for detail panels
* primitive selected/highlighted state
* pick identity that resolves child Coin hits to parent result primitives
* synchronous transaction callbacks for active producers
* explicit custom-provider teardown rules for long-lived Coin callbacks

Owner generation is a freshness fence, not part of feature identity.  A
nonzero generation must prevent stale asynchronous output from replacing newer
results for the same owner.  Generation zero remains the unfenced compatibility
mode for synchronous callers.

Current Interaction State
-------------------------

The feature store can preserve command-result metadata, per-primitive metadata,
selected/highlighted primitive lists, and line-layer child-to-parent primitive
resolution.  Neutral GED APIs expose that data without requiring callers to
include libbrlobol-private record types.

qtcad consumes the bridge for real Obol/Coin pick details.  It keeps raw child
`SoBRLPickDetail` identity, adds resolved parent feature/primitive identity,
copies primitive metadata, and routes resolved command-result or overlay picks
into Obol primitive selected/highlighted state instead of database path
selection.

Custom Coin Provider Policy
---------------------------

Typed records are preferred for common line/HUD/point/face visualizations.
Custom Coin nodes are for complex command or plugin-authored interactions that
need direct Coin scene graph features.  They must remain inside an
owner-scoped Obol boundary that defines:

* replacement, removal, and teardown
* pick identity and primitive-state integration
* callback/sensor/manipulator lifetime
* selection/highlight synchronization
* database-edit invalidation
* structured metadata and transaction callback behavior

The first provider hook exists: GED command-scene producers can publish an
opaque provider-returned `SoNode` as a `CustomNode` feature, interpreted only by
the C++ Obol adapter.  The remaining design work is richer persistent
interaction behavior, not basic node ownership.
