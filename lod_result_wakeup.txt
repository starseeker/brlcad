BRL-CAD LoD Result Wakeup and Scene Refresh Note
================================================

Purpose
-------

This note fills a gap in the staged LoD design: async workers can produce
progressively better representation data, but the scene also needs a reliable
way to know that queued results should be drained and applied to already drawn
nodes.

The current staged LoD direction is correct:

* Background workers produce provider-neutral BRLObolLodResult records.
* BRLObolLodService owns the thread-safe result queue.
* The UI/main thread drains results.
* SoBRLLodUpdateAction matches results to scene nodes and applies accepted
  staged data to Obol fields.
* Applying those fields should trigger normal Obol notification/render dirty
  behavior.

What is missing is a wakeup path from "a worker queued a result" to "the scene
owner schedules a main-thread drain/update pass."  Polling opportunistically
during unrelated render or input events is not robust enough: if the UI is
idle, better cached representations can sit in the result queue indefinitely.


Required Contract
-----------------

Add a lightweight result-ready notification mechanism to BRLObolLodService.
This is not a scene-mutation API and not a direct result-delivery API.  It is
only a wakeup signal telling the owning view/controller that drainResults()
should be called on the UI/main thread soon.

The public service API should add a small subscription surface:

    typedef uint64_t BRLObolLodSubscriberId;

    typedef void (*BRLObolLodResultReadyCB)(
        BRLObolLodService *service,
        void *userData);

    BRLObolLodSubscriberId subscribeResultReady(
        BRLObolLodResultReadyCB callback,
        void *userData);

    void unsubscribeResultReady(BRLObolLodSubscriberId id);

Callback rules:

* The callback is invoked only as a wakeup signal.
* The callback must not mutate Obol nodes.
* The callback must not call drainResults() directly unless the caller already
  knows it is running on the UI/main thread.  The normal pattern is to set a
  pending flag and ask the UI/main loop to wake.
* The service invokes callbacks outside the service mutex.
* The service must tolerate unsubscribe during shutdown and must not call a
  subscriber after unsubscribe returns.
* Callback order is not semantically important.  Correctness comes from
  drainResults(), result identity, and generation/revision checks.


Coalescing Policy
-----------------

Notifications should be coalesced to avoid a wakeup storm when many objects
finish together.

Recommended rule:

* Fire result-ready callbacks only when the published-result queue transitions
  from empty to non-empty.
* Do not fire for every subsequent result while the queue is already non-empty.
* Once the UI/main thread drains the queue to empty, the next published result
  can fire another callback.

This preserves reliable wakeup behavior while keeping notification overhead
bounded.  Losing individual callbacks is acceptable because callbacks do not
deliver results; the queue is the durable handoff.

It is acceptable for a controller to also poll queuedResultCountForDiagnostics()
or drain opportunistically before rendering, but that should be a latency
optimization, not the only correctness mechanism.


Controller Integration
----------------------

BRLObolViewController, or the narrow scene/view owner that owns the active
BRLObolLodService, should subscribe to result-ready notifications.

Recommended controller state:

* BRLObolLodService *lodService
* BRLObolLodSubscriberId lodResultSubscriberId
* an atomic or mutex-protected lodResultsPending flag
* last LoD update counters and diagnostics, if useful for tests/debugging

Recommended callback behavior:

1. Set lodResultsPending.
2. Request a main-loop wakeup or render/update pass.
3. Do not touch scene nodes in the callback.

Recommended main-thread processing method:

    size_t processPendingLodResults(size_t maxResults = 0);

Behavior:

1. Return immediately if there is no scene root or no service.
2. Drain queued results from BRLObolLodService::drainResults().
3. If no results were drained, clear lodResultsPending and return 0.
4. Construct SoBRLLodUpdateAction with the drained results.
5. Apply the action to the scene root on the UI/main thread.
6. Record matched/applied/rejected/unmatched counts and diagnostics.
7. If any result was applied, call requestRender("lod-result").
8. If the service still has queued results after a bounded drain, leave
   lodResultsPending set so another pass will run.

This keeps LoD refresh as normal Obol scene/update behavior.  Workers never
mutate the scene, and scene nodes do not need to subscribe to background
threads individually.


Render Loop Placement
---------------------

The view owner should call processPendingLodResults() before rendering, after
normal scene realization/input revision updates and before issuing the actual
render.  This allows a single frame to consume newly available LoD data and
draw the improved representation immediately.

Suggested places to trigger processing:

* result-ready callback wakes the UI/main loop;
* before render if lodResultsPending is set;
* after explicit LoD submissions for tests or synchronous controller flows;
* optionally during idle processing with a maxResults budget to avoid long UI
  stalls when many large result payloads arrive together.


Stale and Late Result Handling
------------------------------

The existing generation/revision matching remains mandatory:

* BRLObolLodResult carries request/source/view/policy/provider identity.
* SoBRLLodUpdateAction matches results to candidate scene nodes.
* SoBRLMeshShape::applyStagedLodResult rejects stale or mismatched results.
* Rejected, stale, cancelled, cache-miss, and error results are drained and
  diagnosed, not left in the queue.

The wakeup mechanism must not bypass these checks.  It only causes the checks
to run promptly.


Threading and Lifetime Requirements
-----------------------------------

The subscription implementation should be conservative:

* Protect the subscriber list with the existing service mutex or a dedicated
  mutex.
* Copy the subscriber callback/userData pairs to a local vector while holding
  the lock, then release the lock before invoking callbacks.
* Do not invoke callbacks while holding the result-queue mutex.
* During stop/destruction, prevent new callbacks and clear subscribers only
  after worker completion has been coordinated.
* If a subscriber is removed while a callback is already in flight, the service
  may allow that already-copied callback to finish only if the caller contract
  documents that unsubscribe must occur before destroying userData and after
  the UI owner has stopped the service.  Prefer the stronger guarantee if
  practical: unsubscribe waits out in-flight callbacks for that subscriber.


Performance Notes
-----------------

The hot path remains queue push plus an empty-to-nonempty check.  The callback
list should normally be tiny, usually one view/controller owner.  Callback
work should be O(number of subscribers), not O(number of scene nodes or queued
results).

Draining and applying results can be budgeted:

* maxResults == 0 means drain all available results.
* A positive maxResults lets interactive applications spread large update
  bursts over multiple frames.
* If a budget is used and results remain queued, the controller should keep
  lodResultsPending set and request another update/render pass.


Testing Requirements
--------------------

Service tests:

* A subscriber is called when a published result is queued.
* Empty-to-nonempty coalescing fires once for a burst of results before drain.
* After drainResults() empties the queue, a later result fires another wakeup.
* unsubscribeResultReady() prevents future callbacks.
* Callbacks are invoked outside the service mutex.  A test callback should be
  able to call a diagnostic service query without deadlocking.

Controller/update tests:

* Submit an async staged mesh result, observe the pending flag/wakeup, process
  pending results on the main thread, and verify SoBRLMeshShape fields update.
* Applied results request a render with reason "lod-result".
* Stale-generation results are drained, rejected, diagnosed, and do not update
  mesh geometry.
* A bounded drain leaves lodResultsPending set when more queued results remain.

Stress tests:

* Many worker completions should not produce one UI wakeup per result while
  the queue remains non-empty.
* Stopping the service with pending work should not call destroyed subscribers.
* Multiple subscribers, if allowed, should all receive wakeups without affecting
  result queue correctness.


Design Summary
--------------

The LoD API should have a subscription mechanism, but only at the service/view
owner boundary.  Individual scene nodes should not subscribe to background LoD
workers.  The robust model is:

    worker thread
        queues BRLObolLodResult
        emits coalesced result-ready wakeup

    view/controller owner
        wakes UI/main loop
        drains BRLObolLodService results
        applies SoBRLLodUpdateAction to the scene
        requests render if applied results changed nodes

    Obol nodes
        receive accepted staged data through normal field updates
        notify/render dirty through normal Obol mechanisms

This gives reliable progress when the UI is idle, avoids unsafe cross-thread
scene mutation, and keeps result delivery performant and deterministic.
