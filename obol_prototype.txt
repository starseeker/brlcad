Obol-Canonical Next Phase Implementation Guide
==============================================

Status and Direction
--------------------

The initial prototype recommends pivoting toward Obol as BRL-CAD's canonical
drawing scene API.  The working model is:

    Application / GED-like commands
            |
    small BRL-CAD scene services
            |
    Obol scene graph
            |
    BRL-CAD Obol nodes/actions/details
            |
    Obol render manager + application-provided backend/context

The next phase should not re-evaluate this from scratch.  It should stress the
remaining weak points that could still force us to rebuild BSG's generic scene,
render-item, or backend contracts inside Obol.

The architectural target is:

    - Obol is the canonical scene graph and API.
    - libbrlobol contains BRL-CAD-specific Obol nodes, actions, details, and
      narrow application services.
    - libbsg remains reference material for BRL-CAD semantics and a fallback
      until the Obol path covers production needs.
    - libdm is not used by the new path except for explicit compatibility
      experiments.
    - BRL-CAD code that needs drawing API access may be C++.


Baseline Already Proven
-----------------------

The initial libbrlobol prototype lives under:

    include/brlobol/
    include/brlobol.h
    src/libbrlobol/

It already demonstrates:

    - BRL-CAD database source nodes as ordinary Obol nodes.
    - Explicit realization with SoBRLRealizeAction.
    - Real .g path traversal through librt/db_walk_tree().
    - Per-leaf Obol transform nodes preserving combination instance matrices.
    - SoBRLVListShape for wire/point geometry.
    - SoBRLMeshShape for minimal indexed triangle geometry.
    - Database-backed shaded realization for ARB8/RPP and BoT leaves as
      SoBRLMeshShape nodes, selected by SoBRLDatabaseSource::drawMode.
    - Generalized NMG tessellation fallback for shaded primitives without a
      direct mesh importer, proven with real database sphere, ellipsoid, TGC,
      and torus leaves and still exposed as ordinary SoBRLMeshShape scene
      content.
    - Existing-model shaded hierarchy coverage: pinewood.g, when present in
      the test environment, realizes many shaded mesh leaves and is measured
      and exported through normal Obol actions.
    - Explicit SoBRLDatabaseSource tessellation tolerance fields controlling
      wire/mesh realization policy as scene state rather than hidden controller
      state.
    - Obol pick details carrying BRL-CAD identity.
    - Snap, measure, and export actions using Obol traversal/model state.
    - SoBRLSnapAction policy controls for enabled snap kinds and selected-only
      filtering, world/path-local coordinate space, and feature-priority
      tie-breaking, with endpoint, midpoint, center, line-nearest, and mesh
      face-nearest candidates, plus opt-in construction-plane policy.
    - SoBRLMeasureAction mesh-face traversal with transformed bounds, surface
      area, triangle count, nearest face identity, and world/path-local
      coordinate reporting, plus connected line-segment angle reporting.
    - Per-shape draw-intent fields for visibility, selectability, selection,
      highlighting, ghosting, hidden-line intent, edit emphasis, LoD policy,
      and color override on wire and mesh geometry.  Pick, snap, measure,
      export, bounds, and GL render paths honor the relevant fields, and export
      records carry the complete backend handoff state.
    - Basic edit preview as ordinary scene content.
    - Obol field-sensor invalidation for database and preview nodes.
    - A narrow SoBRLSceneController service that runs realization passes and
      records diagnostics without owning a duplicate scene hierarchy.
    - Per-source realization diagnostics on SoBRLDatabaseSource, aggregated by
      SoBRLRealizeAction and SoBRLSceneController for failed database source
      realization.
    - Partial source refresh: changing one source's input/view revision marks
      only that scene node stale, and the controller refreshes only that source.
    - Controller rebuild from the existing Obol scene: stale state remains on
      the scene nodes rather than in controller side tables.
    - Obol sensor-queue driven updates: a scheduled Obol sensor mutates a
      BRL-CAD source node field, the source's own field sensors mark it stale,
      and SoBRLSceneController refreshes the scene without a BRL-CAD event
      side table.
    - Basic grid, axes, and ADC overlays as Obol nodes.
    - Direct Obol GL rendering for vlist geometry.
    - A second non-GL renderScene() backend proof using an application-owned
      ContextManager.
    - A production-relevant NanoRT backend proof: a generated BRL-CAD .g
      database source realizes to SoBRLMeshShape, renders through Obol's
      application-owned SoNanoRTContextManager path, exposes framebuffer
      readback, and composites direct Obol HUD overlays without libdm.
    - Obol ContextManager diagnostic reporting: SoOffscreenRenderer now reports
      backend renderScene fallback through the application-provided context
      manager, and libbrlobol tests verify the callback path.
    - Direct Obol SoHUDKit, SoHUDLabel, and SoHUDButton use in the same
      BRL-CAD scene, including screen-space title/status/scale text and a
      button/selection-rectangle stand-in.
    - GL rendering and non-GL renderScene() overlay collection/composition for
      the same BRL-CAD + HUD scene, without libdm or a BRL-CAD HUD command
      stream.
    - Obol SoDB::init() now initializes nodekits, so normal Obol
      initialization is sufficient before direct SoHUDKit use.

That is enough evidence to proceed with Obol-canonical work.  The next phase is
about finding the remaining cases where this model might break down.


Core Rule
---------

Every new feature should first be expressed as normal Obol scene programming:

    - node fields for persistent scene state
    - field sensors or notification for invalidation
    - actions for realization, export, snap, measure, and diagnostics
    - details for pick results
    - state/elements only when traversal state is genuinely needed
    - application-owned backends via Obol's context/backend interface

Do not add a generic BRL-CAD node/field/action/render layer unless a concrete
test shows Obol cannot represent the needed behavior cleanly.


BSG-Reimplementation Risk Tests
-------------------------------

The next phase should answer these questions directly.

1. Editor and update lifecycle

    Question:

        Can live editing, database invalidation, undo/redo style revision
        changes, animation/timers, and efficient partial updates remain normal
        Obol node/field/sensor/action behavior?

    Implement:

        - DONE: Add a small SoBRLSceneController application service.  The
          current version coordinates realization passes and diagnostics, but
          does not own a second scene graph.
        - DONE: Extend SoBRLDatabaseSource stale state beyond a boolean:

              staleReason
              sourceRevision
              inputsRevision
              viewRevision
              realizedSourceRevision
              realizedInputsRevision
              realizedViewRevision

        - DONE: Add partial update tests where only one source under a larger
          scene is invalidated and refreshed.
        - DONE: Add edit-preview replacement tests where published preview
          geometry is replaced repeatedly without stale children, dangling pick
          details, or external lookup tables.  The prototype now verifies that
          export, pick, snap, and measure traversals see only the current Obol
          preview child subtree after repeated replacement.
        - DONE: Add an Obol sensor-driven update test.  The prototype schedules
          an Obol one-shot sensor that mutates a BRL-CAD source field, lets
          the source field sensors mark the node stale, and verifies that
          SoBRLSceneController refreshes only the updated scene state.

    Acceptance:

        - Field changes invalidate the right nodes without application side
          tables.
        - Realization updates only stale nodes unless explicitly forced.
        - Pick/snap/measure/export results agree after repeated updates.
        - The controller can be deleted and rebuilt from the Obol scene plus
          application database handles.

    BSG warning sign:

        - The controller stores the authoritative tree, transforms, visibility,
          or draw state outside Obol.

2. Production geometry representation

    Question:

        Can real BRL-CAD display geometry be represented as typed Obol shapes
        without reintroducing bsg_payload or bsg_render_item as the public API?

    Implement:

        - DONE: Promote SoBRLMeshShape from minimal test shape to the
          main shaded geometry carrier.  The current prototype realizes real
          database ARB8/RPP, BoT, tessellated curved leaves, and an existing
          pinewood.g hierarchy into SoBRLMeshShape nodes, including bounds,
          pick detail, snap, measure, export, and draw-mode replacement tests.
        - DONE: Add a tessellation realization path for common
          primitives and BoTs.  BoT direct conversion is covered, and the NMG
          tessellation fallback is now proven on sphere, ellipsoid, TGC, and
          torus primitives, plus the existing pinewood.g hierarchy when
          available.  Failed database source realization records source-local,
          action-level, and controller-level diagnostics.  Basic tessellation
          tolerance policy is represented by SoBRLDatabaseSource fields and
          covered by invalidation/re-realization tests.  Remaining
          production work is now breadth hardening rather than an unanswered
          BSG-reimplementation risk.
        - Preserve source path, primitive/face/edge/vertex identity, and
          material/draw intent on Obol nodes or fields.
        - Keep vlist/wire data and mesh data as Obol shape fields or compact
          internal storage owned by Obol nodes.
        - DONE: Add bounding-box, primitive-generation, GL render, pick,
          export, and diagnostic coverage for mesh geometry.  SoBRLMeshShape
          implements Obol shape bounds, primitive generation, GL rendering,
          ray-pick details, export traversal, snap/measure traversal, and
          realized database mesh tests, with render/backend coverage through
          OSMesa and NanoRT.

    Acceptance:

        - A mixed wire + shaded model can be rendered, picked, snapped,
          measured, and exported from the Obol scene.
        - Backend export is an Obol action or backend traversal, not a public
          render-item list.
        - The same identity model works for reused primitives under different
          combination paths.

    BSG warning sign:

        - Most shapes are opaque references into a global BRL-CAD payload store
          and Obol traversal cannot answer pick/export/measure questions without
          bypassing the scene graph.

3. Snap and measurement policy

    Question:

        Can richer CAD interaction policies be layered onto Obol actions and
        details without rebuilding BSG interaction records?

    Implement:

        - DONE: Extend SoBRLSnapAction with policy fields:

              enabledKinds
              tolerance
              coordinateSpace
              selectionFilter
              priorityPolicy

          Enabled snap kinds, tolerance, selected/unselected filtering,
          world/path-local coordinate-space variants, feature-priority
          tie-breaking, and opt-in construction-plane policy are covered.  More
          sophisticated application policies can still be added as action
          fields if needed.

        - DONE: Add endpoint, midpoint, center, edge-nearest,
          face-nearest, grid, construction-plane, and active-edit snaps as
          needed.  Endpoint, midpoint, center, line-nearest/edge-nearest,
          grid/overlay, active edit-preview geometry, and mesh face-nearest
          candidates are covered.  Construction-plane snapping is covered as
          action policy rather than scene geometry.
        - DONE: Extend SoBRLMeasureAction to report distances, angles,
          face areas, path-local coordinates, and model/world coordinate
          variants.  Mesh face area, triangle count, transformed bounds,
          nearest face identity, connected line-segment angle reporting, and
          explicit world/path-local coordinate variants are covered.
        - Use SoBRLPickDetail or related details to share identity between
          picking, snapping, and measurement.

    Acceptance:

        - Snap/measure traversal works across transformed database instances,
          edit previews, overlays, and mesh faces.
        - World-space and path-local interaction variants are action policy,
          not alternate interaction geometry.
        - Policies are action fields or application inputs, not alternate
          render batches.
        - Results carry enough BRL-CAD identity to drive editing commands.

    BSG warning sign:

        - Snap and measure require a separate traversable interaction scene
          that duplicates Obol transforms and shape identity.

4. HUD, faceplate, and screen-space overlays

    Question:

        Can faceplate/HUD behavior use Obol-native overlay, text, and screen
        space mechanisms without a parallel BRL-CAD HUD renderer?

    Implement:

        - DONE: Keep model-space helpers such as grid, axes, and ADC as normal
          Obol nodes.
        - DONE: Add screen-space/view-anchored tests for labels, framebuffer
          status, scale indicators, rubber-band selection, and command
          feedback.  The current render test uses SoHUDKit with label/status
          text and a SoHUDButton selection/control rectangle in the same scene
          as BRL-CAD geometry.
        - DONE: Prefer existing Obol nodes such as SoHUDLabel, SoHUDButton,
          SoText2, SoText3, cameras, and overlay collection paths.
        - Add BRL-CAD nodes only when they encode BRL-CAD-specific semantics,
          not just because text or 2D drawing is needed.
        - DONE: Verify GL and non-GL backend behavior for the same HUD scene.
          OSMesa GL renders the HUD through Obol, and the non-GL test backend
          collects and composites multiple Obol overlays via SoSceneCollector.

    Acceptance:

        - HUD state is visible in the Obol scene.
        - Direct Obol HUD/text nodes work beside BRL-CAD nodes.
        - Backends can collect/render HUD content without libdm.
        - Remaining follow-up, if needed for application UX, is event-driven
          mutation/callback coverage for live rubber-band drag and HUD control
          activation.  The scene representation itself does not currently show
          a need for a new BSG-style HUD layer.

    BSG warning sign:

        - A new public BRL-CAD HUD command stream becomes the only way to draw
          labels, status text, and screen-space controls.

5. Backend and libdm replacement

    Question:

        Does Obol's application-provided backend/context interface cover the
        real backend needs that historically lived in libdm?

    Implement:

        - DONE: Keep the OSMesa and software renderScene() tests.  The same
          BRL-CAD + HUD scene now renders through both paths.
        - DONE: Add one production-relevant backend path: system GL/Qt,
          NanoRT, Embree, or another Obol backend available in this tree.
          The current prototype adds a BRL-CAD database-backed NanoRT render
          test.  It creates a real .g database, realizes a shaded source into
          Obol mesh content, renders the same root scene through OSMesa GL and
          through SoOffscreenRenderer plus SoNanoRTContextManager, verifies
          framebuffer readback, and verifies direct Obol HUD overlay
          composition.  No libdm calls are involved.
        - DONE: Define the minimum application backend interface BRL-CAD
          needs.  Current tests exercise:

              context lifetime
              viewport resize
              render begin/end
              framebuffer readback
              diagnostic RGB file output
              overlay/HUD composition
              backend diagnostic reporting
              scene pick after production-backend rendering

          Pick and selection remain Obol scene/action behavior in the current
          prototype.  The NanoRT backend proof now renders a BRL-CAD scene and
          then picks the same scene through SoRayPickAction/SoBRLPickDetail,
          so backend-assisted picking is not part of the minimum interface
          unless a future backend acceleration API is deliberately added.

        - DONE: Exercise readback, framebuffer visibility, and diagnostic
          image file output without libdm.  The NanoRT backend test writes its
          rendered buffer through Obol's SoOffscreenRenderer::writeToRGB path.
        - DONE: Exercise backend diagnostic hooks without libdm.  The render
          test installs an application ContextManager, declines renderScene(),
          and verifies that SoOffscreenRenderer reports the fallback through
          the context diagnostic callback.
        - Keep backend-specific acceleration private to the backend or to
          internal action results, not to the public scene API.

    Acceptance:

        - DONE: The same Obol root scene renders through at least two serious
          backend paths.  The parity test uses one realized BRL-CAD
          database-backed shaded source plus direct Obol HUD overlays and
          renders it through both OSMesa GL and NanoRT.
        - DONE: Backend handoff can be implemented by Obol traversal/action
          APIs.  Current picking and selection use Obol scene actions/details
          after backend rendering rather than a libdm-style backend pick API.
        - BRL-CAD application code does not call dm_draw_* on the new path.

    BSG warning sign:

        - A new libdm-shaped adapter becomes the real API and Obol is only a
          serialization source for that adapter.

6. Visibility, selection, highlighting, and draw intent

    Question:

        Can common viewer state be normal Obol fields/state rather than a
        separate BRL-CAD display list?

    Implement:

        - DONE: Define SoBRLDrawIntent or equivalent fields for:

              wire/shaded/both
              hidden-line intent
              selection/highlight state
              ghosted/transparent state
              per-path color overrides
              edit-mode emphasis
              LoD policy

          The prototype stores visibility, selectability, selected,
          highlighted, ghosted, hidden-line intent, edit emphasis, LoD policy,
          and explicit color override state directly on SoBRLVListShape and
          SoBRLMeshShape nodes.  Wire/shaded/both is represented by source
          drawMode and ordinary Obol scene contents.  Bounds, pick, snap,
          measure, export, and GL render paths honor visibility, while pick
          and snap also honor selectability.  Export records carry the complete
          draw-intent field set for backend handoff.  Default geometry still
          inherits ordinary Obol color/material state unless the BRL-CAD color
          override field is enabled.

        - Use Obol material/style nodes where they are sufficient.
        - DONE: Add selection and highlight tests for whole paths and
          sub-entities.  Whole leaf-instance visibility, selectability,
          selection, highlight, and ghost state are covered for reused database
          primitives.  Mesh face and wire segment selection/highlight intent is
          covered by export and measurement tests, and selected-only snapping
          is covered for mesh faces.
        - DONE: Verify that hiding, showing, recoloring, selecting, hidden-line
          intent, edit emphasis, and LoD policy update Obol scene state without
          regenerating unrelated geometry.  These are covered as in-place field
          changes on realized Obol shapes.

    Acceptance:

        - Selection/highlight state can be inspected from the scene.
        - Render, pick, snap, measure, and export agree about visibility and
          selection filters.
        - Per-path overrides work for reused primitives under different
          combination paths.

    BSG warning sign:

        - Visibility and highlight become authoritative in a separate display
          table and only get copied into Obol at render time.


Implementation Order
--------------------

Use this order for the next phase.  Each step should end with tests.

1. Stabilize libbrlobol as a C++ Obol extension library

    - Keep the public API small.
    - DONE: Document class ownership and database-handle ownership.  Public
      headers now state that SoBRLDatabaseSource borrows db_i handles,
      SoBRLSceneController borrows the Obol scene root, and brlobol_init()
      borrows the application context manager.
    - DONE: Make initialization explicit:

          brlobol_init(contextManager)

      Rendering tests assert that brlobol_init() installs the supplied
      application ContextManager.  The NULL fallback remains available only by
      explicit call and is documented for non-rendering tests.

2. Add scene lifecycle service

    - Implement SoBRLSceneController only if needed to coordinate application
      policy.
    - It may track diagnostics and schedule actions.
    - It must not own a duplicate hierarchy or transform state.

3. Expand production geometry

    - DONE: Add tessellated mesh realization for selected primitives.
    - DONE: Add BoT coverage.
    - DONE: Add source-level tessellation tolerance fields and verify that
      changing them invalidates and re-realizes database mesh geometry.
    - DONE: Add draw-intent/material fields.
    - DONE: Extend export tests from synthetic triangles to realized database
      mesh geometry and an existing shaded hierarchy when pinewood.g is
      available.

4. Expand interaction semantics

    - DONE: Extend pick detail identity for realized line and mesh geometry.
    - DONE: Extend snap policies.  Endpoint, midpoint, center,
      line-nearest, mesh face-nearest, selection filtering, feature priority,
      world/path-local coordinates, overlays, active edit-preview geometry, and
      construction-plane snapping are covered.
    - DONE: Extend measure outputs for line length, mesh face area, nearest
      primitive identity, world/path-local coordinates, and connected
      line-segment angles.
    - DONE: Add selection/highlight filtering.  Snap supports selected-only
      and unselected-only policies, and measurement supports selected-only,
      unselected-only, highlighted-only, and unhighlighted-only policies over
      whole-shape and per-primitive intent fields.

5. Expand overlay/HUD coverage

    - DONE: Keep geometric helpers as scene nodes.
    - DONE: Add screen-space text/status/rubber-band tests.
    - DONE: Verify GL and non-GL paths.
    - DONE: Add sensor-driven scene mutation coverage for source realization.
    - Optional next check: mutate HUD state from an interaction callback to
      prove live drag/control behavior, rather than static rendering.

6. Add a production backend proof

    - DONE: Use NanoRT as the current production-relevant backend proof.
    - DONE: Keep all backend communication behind Obol context/backend APIs.
    - DONE: Add direct framebuffer readback tests.
    - DONE: Add screenshot/file-output convenience tests.  NanoRT diagnostic
      RGB output is written from the Obol renderer path without libdm.
    - DONE: Add backend diagnostic-hook tests.  Obol's ContextManager now has
      a diagnostic callback and libbrlobol verifies SoOffscreenRenderer fallback
      reporting through it.

7. Compare API surface

    - DONE: List public libbrlobol headers and classes.
    - DONE: List current service APIs.  SoBRLSceneController is the only
      service-style public API at this stage.
    - DONE: Compare against the relevant libbsg/libdm concepts.
    - DONE: Identify anything that looks like generic scene infrastructure.
      Current public libbrlobol does not expose a generic node/field graph,
      public render items, backend scenes, immediate dm drawing, or a separate
      interaction scene.


Test Matrix
-----------

Each milestone should add tests that use real scene traversal where possible.

Required model cases:

    - synthetic source for small deterministic checks
    - generated two-instance hierarchy for transform/path identity
    - existing hierarchy model such as share/db/pinewood.g or share/db/havoc.g
      (pinewood.g is covered when available in the test environment)
    - BoT and tessellated curved models

Required operation cases:

    - realize
    - render
    - bounding box
    - pick
    - snap
    - measure
    - export/backend handoff
    - edit preview update
    - field invalidation
    - selection/highlight
    - HUD/overlay rendering
    - framebuffer readback

Required backend cases:

    - OSMesa/offscreen GL
    - one non-GL or raytracing-style backend
    - one production application backend if available

Required negative checks:

    - no libdm calls in the new path
    - no public bsg_render_item equivalent
    - no authoritative side table for hierarchy, transforms, visibility, or
      identity
    - no duplicate interaction scene for snap/measure


Current API Surface Audit
-------------------------

The current public libbrlobol headers are intentionally much smaller than the
current libbsg/libdm surface.  They expose:

    - initialization:

          brlobol_init(contextManager)

    - BRL-CAD scene/source nodes:

          SoBRLDatabaseSource
          SoBRLEditPreview

    - BRL-CAD geometry shapes:

          SoBRLVListShape
          SoBRLMeshShape

    - BRL-CAD overlay/helper nodes:

          SoBRLGrid
          SoBRLAxes
          SoBRLADC

    - BRL-CAD traversal/policy actions:

          SoBRLRealizeAction
          SoBRLSnapAction
          SoBRLMeasureAction
          SoBRLExportAction

    - BRL-CAD pick identity:

          SoBRLPickDetail

    - one narrow application service:

          SoBRLSceneController

This maps cleanly to Obol extension points: nodes, fields, actions, details,
and application services.  It does not currently expose public equivalents of:

    - bsg_node/bsg_group/bsg_field as a second generic scene graph
    - bsg_payload or a global payload store
    - bsg_render_item or bsg_render_batch
    - bsg_backend_scene or a public backend adapter scene
    - dm_draw_* immediate drawing as the new rendering contract
    - a BRL-CAD HUD command stream
    - a separate snap/measure interaction scene

That API shape is evidence in favor of the Obol-canonical pivot.  The main
watch item is not API count by itself; it is whether future production work
forces libbrlobol to add generic scene, field, render-item, or backend-adapter
types that duplicate Obol.  If that happens, the pivot should pause and the
team should either move the missing abstraction into Obol proper or keep libbsg
as the canonical semantic drawing layer.


Public API Guidance
-------------------

Prefer these public concepts:

    - SoBRLDatabaseSource
    - SoBRLEditPreview
    - SoBRLVListShape
    - SoBRLMeshShape
    - SoBRLDrawIntent or equivalent draw-intent fields
    - SoBRLGrid
    - SoBRLAxes
    - SoBRLADC
    - SoBRLPickDetail
    - SoBRLRealizeAction
    - SoBRLSnapAction
    - SoBRLMeasureAction
    - SoBRLExportAction

Keep these out of the public API unless a later test proves they are necessary:

    - generic BRL-CAD node handles
    - generic BRL-CAD field handles
    - generic BRL-CAD action handles
    - render batches
    - render items
    - backend scenes
    - appearance actions that duplicate Obol material/style traversal
    - HUD command streams
    - display-list compatibility handles

If an internal render plan is needed for batching, ray tracing, export, or
backend acceleration, keep it an implementation detail produced from Obol
traversal.  It should not become the canonical scene API.


Compatibility Policy
--------------------

Compatibility is not the first goal of the next phase.  The first goal is to
validate the clean canonical model.

Later compatibility decisions:

    - Tcl/GED integration can call C++ scene services or thin C wrappers.
    - plot3/tig/vectfont compatibility should be implemented as import/export
      or specialized Obol nodes only if still needed.
    - old libdm immediate drawing APIs should not shape the new API.
    - framebuffer compatibility should be tested through Obol backend/readback
      services first.


Decision Gates
--------------

Continue the Obol-canonical pivot if:

    - new features are naturally expressed as Obol nodes, fields, actions, and
      details
    - backend support uses Obol context/backend hooks
    - direct Obol features such as HUD/text remain usable in BRL-CAD scenes
    - scene state is inspectable and serializable through Obol mechanisms where
      appropriate
    - libbrlobol stays focused on BRL-CAD semantics

Pause and reconsider if:

    - bsg_render_item or bsg_render_batch reappears as the public contract
    - a second authoritative hierarchy is needed outside Obol
    - transforms, visibility, selection, or draw intent must be duplicated in
      side tables
    - snap/measure/export cannot use Obol traversal without major bypasses
    - backend support turns into a new libdm with Obol only feeding it

The expected outcome is not a one-to-one port of libbsg to C++.  The expected
outcome is a smaller BRL-CAD extension layer on top of Obol.  If the next phase
cannot keep that shape, the correct fallback is to keep libbsg as the semantic
drawing layer and use Obol as one backend/runtime target.
